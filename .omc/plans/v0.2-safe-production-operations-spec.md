# OpenLander v0.2.0 - Safe Production Operations Spec

Date: 2026-06-02
Status: internal planning
Related roadmap: `.omc/roadmap/v0.2-roadmap.md`
Baseline: public v0.1.9 stabilization work, before v0.1.9 tag

## Summary

v0.2.0 should make OpenLander safe to use for production operations before we
expand into autonomous AI Ops, Swarm, Kubernetes, or one-click self-update.

The feature is:

> First-class environments plus protected deploy policy across web, REST, MCP,
> and the deploy pipeline.

In plain terms:

- Users can clearly separate `development`, `staging`, and `production`.
- Deploys, logs, status, rollback, env vars, and service connections are scoped
  to the selected environment.
- Production can require approval before a human or MCP agent mutates it.
- Agents receive enough structured guidance to avoid guessing which
  environment they are touching.

## Why This Comes Next

OpenLander's current core loop is already useful:

- deploy Git/image workloads;
- run managed services;
- expose logs, status, topology, and diagnostics;
- let external MCP agents operate explicitly;
- keep built-in autonomous AI dormant in 0.1.

The next risky boundary is not "more automation"; it is "safe operation of
real production systems." Without environment and approval primitives, future
AI Ops, update buttons, registry auth, and runtime backends all become harder
to reason about.

v0.2.0 therefore builds the safety layer that later features can reuse.

## Current Model

The post-0012 data model has mostly resolved the old Project/Service confusion:

- `projects` is group-only.
- `services` owns deployable and managed service rows.
- `service_connections` links consumer/provider services.
- `environments` is service-scoped and currently supports only
  `production` and `development`.
- `env_vars` is group-scoped with optional service and environment overrides.
- deploy locks remain project/group-scoped.
- `action_runs` already has a `pending_approval` state and approval metadata.
- `RuntimeBackend` exists, but Docker is the only runtime.

v0.2.0 should not re-open the whole data split. It should add project-level
environment policy and make existing service runtime environments line up with
that policy.

## Product Scope

### Must Have

1. Project environments
   - Each project has canonical environment definitions:
     `production`, `staging`, and `development`.
   - Environment definitions carry policy and display metadata.
   - Production is protected by default for new projects.

2. Environment-aware deploy flow
   - New deploy plans include target environment identity.
   - Redeploy, rollback, stop, start, status, logs, and topology preserve the
     target environment.
   - Staging and development deploys must not accidentally overwrite production
     containers, ports, routes, env vars, or deploy history.

3. Environment-scoped configuration
   - Env vars can be project-wide, service-specific, and environment-specific.
   - The UI makes inheritance and override source clear.
   - Deploy-time env resolution uses the selected environment.

4. Protected production operations
   - Production deploy/redeploy/rollback can require approval.
   - Approval records are durable enough for page refresh and process restart
     behavior to be predictable.
   - MCP-triggered protected actions return a pending status with a poll call.

5. Web UX
   - Project and Service detail pages show the active environment.
   - Users can switch environment context without navigating through confusing
     duplicate pages.
   - Pending production approvals are visible and actionable.

6. MCP agent UX
   - Composite deploy/service/project tools accept an explicit environment key
     where relevant.
   - Responses include environment identity and next calls using only the stable
     call-helper fields: `status_call`, `diagnostic_call`, `suggested_call`,
     and `poll_call`.
   - Validation errors should guide an agent toward a valid environment/action
     combination without repeating invalid input.

7. Release gate
   - Unit and contract tests cover schema, policy, MCP, REST, and pipeline
     behavior.
   - E2E covers one staging deploy path and one protected production path.

### Should Have

- Environment badges on recent deploys, activity, and topology.
- Environment filter on deploy history.
- Clear default branch per environment.
- A policy summary in deploy confirmation UI.
- Backward-compatible defaults for existing API/MCP calls that omit
  environment.

### Nice To Have

- Service-level policy override on top of project environment policy.
- Custom environment keys beyond the canonical three.
- Public preview URLs for staging by default.
- Per-environment managed service instances.

These should not block v0.2.0 unless implementation proves cheaper than
expected.

## Explicit Non-Goals

- No built-in autonomous AI Ops re-enable.
- No Kubernetes, k3s, or Docker Swarm runtime.
- No one-click self-update implementation.
- No broad notification center.
- No public MCP helper fields beyond the existing response contract.
- No breaking rename of existing MCP actions without aliases.
- No project/service data-model rewrite beyond environment policy needs.

## Key Product Decisions

### D1. Fixed Environments First

v0.2.0 should ship fixed canonical keys:

- `production`
- `staging`
- `development`

Custom environments are useful, but they multiply routing, branch, policy, and
UI cases. Keep the schema forward-compatible with custom keys, but expose only
the canonical three in v0.2.0.

### D2. Production Defaults To Protected

For new projects:

- `production.requires_approval = true`
- `staging.requires_approval = false`
- `development.requires_approval = false`

For migrated projects:

- preserve current behavior where possible;
- create production as protected in UI copy, but do not strand existing
  unattended workflows without a visible migration note;
- use a one-time migration flag or release note if compatibility requires
  production approval to default off for existing installs.

Recommended final decision: new projects protected by default, migrated
projects receive production policy with approval disabled but a UI warning that
lets the operator enable it.

### D3. Project Policy, Service Runtime

Use two layers:

- `project_environments`: the policy/display definition for a project.
- `environments`: the runtime state of a specific service in a project
  environment.

This avoids overloading service runtime rows with project-level policy and keeps
the existing pipeline shape close to today's code.

### D4. Project-Level Deploy Lock Remains

Keep the deploy lock on `projects` for v0.2.0.

Environment-level concurrent deploys are attractive, but they add risk around
shared ports, service connections, Traefik updates, compose stacks, and managed
service mutation. A future version can split locks after environment behavior is
well tested.

### D5. Production Route Compatibility

Production should retain existing route/container naming as much as possible.

Recommended convention:

- production uses the current stable public route and container naming;
- staging/development add an environment suffix where the runtime name must be
  unique;
- API and UI never infer environment from URL string shape; they use stored
  environment identity.

### D6. Update Button Is Later Roadmap

An update button is valuable, but self-updating the control plane is risky. It
touches Docker, compose files, database migrations, backups, permissions, and
rollback of OpenLander itself.

Roadmap placement:

- v0.2.3: update awareness only.
- v0.3.0: guided self-update for supported install shapes.

v0.2.0 should not implement self-update.

## Data Model Spec

### New Table: `project_environments`

Purpose: project-level environment definitions and deploy policy.

Fields:

| Field | Type | Notes |
| --- | --- | --- |
| `id` | text pk | UUID or deterministic migration id |
| `project_id` | text fk projects(id) | cascade delete |
| `key` | text | canonical key: production/staging/development |
| `display_name` | text | user-facing label |
| `description` | text nullable | optional explanatory copy |
| `protected` | integer/bool | whether destructive actions are protected |
| `requires_approval` | integer/bool | whether deploy/rollback needs approval |
| `auto_deploy_enabled` | integer/bool | reserved for future webhook/autodeploy |
| `default_branch` | text nullable | environment default branch |
| `sort_order` | integer | production first in stable UI order |
| `archived_at` | text nullable | future custom env retirement |
| `created_at` | text | timestamp |
| `updated_at` | text | timestamp |
| `server_id` | text | default `local` |

Indexes and constraints:

- unique `(project_id, key)`.
- index `(project_id)`.
- check key in canonical set for v0.2.0 if custom envs are not exposed.

### Extend Table: `environments`

Current meaning: runtime state for a service/environment pair.

Add:

| Field | Type | Notes |
| --- | --- | --- |
| `project_environment_id` | text nullable fk | backfilled where possible |
| `key` | text nullable | denormalized key for compatibility/query speed |
| `last_deploy_id` | text nullable | optional, if deploy log linking needs it |
| `policy_snapshot` | text nullable | JSON snapshot used for protected actions |

Compatibility:

- Keep existing `type` in v0.2.0.
- Expand `type` to include `staging`, or migrate callers to `key` and leave
  `type` as legacy.
- Do not drop `type` in v0.2.0.

Recommended implementation:

- Add `project_environment_id`.
- Expand `type` enum/check to `production`, `staging`, `development`.
- Add unique `(service_id, project_environment_id)`.
- Keep existing unique `(service_id, type)` until all callers are moved, then
  drop later.

### Env Vars

`env_vars` already has:

- `project_id`
- optional `service_id`
- optional `environment_id`

v0.2.0 should make environment targeting explicit in API and UI without
rewriting the table.

Recommended behavior:

- `environment_id = null`: project/service shared value.
- `environment_id = runtime environments.id`: environment override.
- deploy-time resolution uses the selected service runtime environment id.
- UI can show inherited value source:
  `project`, `service`, `environment`.

Future option:

- Add `project_environment_id` to `env_vars` if the product needs values before
  a service runtime environment exists. For v0.2.0, prefer creating the service
  runtime environment eagerly when needed.

### Deploy Plans

`deploy_plans.plan_json` already carries most plan details. v0.2.0 should store
environment identity in both plan JSON and queryable columns if needed.

Recommended additions:

- `project_environment_id` nullable.
- `environment_id` nullable.
- `service_id` nullable if not already present in the active branch.

Minimum acceptable:

- Keep columns unchanged and store environment identity in `plan_json`, but add
  repo helpers/tests that guarantee it round-trips.

Preferred:

- Add queryable IDs so approval, status, and history pages do not parse JSON for
  ordinary filtering.

### Action Runs And Approvals

Reuse `action_runs` where practical. It already models:

- `pending_approval`
- `approval_status`
- `approval_tool`
- `approval_requested_at`
- `approval_resolved_at`

Add only if needed:

- `target_project_environment_id`
- `target_environment_id`
- `target_service_id`
- `request_payload_json`
- `approval_reason`

If adding those fields is too invasive, store a compact JSON target payload in
`plan` or `steps_json` for v0.2.0 and add typed columns later.

Hard rule: protected production actions must not depend only on in-memory
approval state.

### Migration Plan

Migration name: next available migration after the active public branch.

Steps:

1. Create `project_environments`.
2. Insert canonical rows for every existing project:
   - production
   - staging
   - development
3. Backfill `environments.project_environment_id`:
   - production -> matching project production environment
   - development -> matching project development environment
   - no existing staging runtime row is required until first staging deploy
4. Expand environment type validation to include `staging`.
5. Add indexes and unique constraints.
6. Add deploy plan/action run columns if chosen.
7. Do not delete old columns.
8. Add migration audit assertions:
   - every project has exactly one canonical row per key;
   - every existing production/development runtime environment links to a
     project environment;
   - env var rows are untouched;
   - deploy log rows remain linked to the same runtime environment.

Rollback:

- Safe rollback can drop new columns/tables only before new v0.2 writes exist.
- After v0.2 writes, rollback should be documented as restore-from-backup.
- Release gate should run a dry migration on a representative pre-v0.2 DB.

## Backend Spec

### Domain Types

Introduce a public internal type:

```ts
type ProjectEnvironmentKey = 'production' | 'staging' | 'development';
```

Keep `OpenLanderEnv` compatible, but avoid spreading old `production |
development` assumptions.

Add internal structs:

- `ProjectEnvironmentPolicy`
- `ResolvedDeployEnvironment`
- `ProtectedOperationDecision`

### Repositories

Add `ProjectEnvironmentRepo`:

- `listByProject(projectId)`
- `findByKey(projectId, key)`
- `ensureCanonical(projectId)`
- `createCanonicalForProject(projectId)`
- `updatePolicy(projectId, key, patch)`
- `archive(projectId, key)` only if custom environments are included later

Extend `EnvironmentRepo`:

- `findByServiceAndProjectEnvironment(serviceId, projectEnvironmentId)`
- `ensureForServiceEnvironment(serviceId, projectEnvironmentId, defaults)`
- `listByProjectEnvironment(projectId, key)`

Extend deploy/action repos only as needed by selected column strategy.

### Policy Service

Add a small policy owner rather than duplicating checks in routes/tools:

- `resolveProjectEnvironment(projectId, environmentKey)`
- `resolveServiceEnvironment(serviceId, environmentKey)`
- `assertEnvironmentMutable(target, operation)`
- `maybeCreateApprovalRequest(target, operation, actor)`

This should be the single place where production protection is evaluated.

### REST API

Add or extend endpoints:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/projects/:projectId/environments` | list project environment definitions and service summaries |
| PATCH | `/api/projects/:projectId/environments/:key` | update display/policy/default branch |
| GET | `/api/projects/:projectId/environments/:key` | environment detail |
| GET | `/api/projects/:projectId/services/:serviceId/environments` | service runtime environments |
| POST | `/api/projects/:projectId/services/:serviceId/environments/:key/ensure` | create runtime env if absent |
| GET | `/api/action-runs?approval_status=pending` | continue using existing pending approval surface |
| POST | `/api/action-runs/:id/approve` | approve protected action |
| POST | `/api/action-runs/:id/reject` | reject protected action |

Extend existing deploy endpoints:

- deploy/redeploy accepts `environment_key`.
- rollback accepts `environment_key` or `environment_id`.
- status/logs/history can filter by `environment_key`.

Backward compatibility:

- omitted environment means `production`.
- responses include environment identity.
- old production-only callers keep working.

### Pipeline

Add environment identity to:

- `DeployConfig`
- `CreatePlanOptions`
- `PlanExecutionContext`
- deploy queue job metadata
- deploy log writes
- rollback target resolution
- topology assembly

Expected flow:

1. Resolve project environment by key.
2. Resolve or create service runtime environment.
3. Check policy.
4. If approval required:
   - create/update action run as `pending_approval`;
   - return pending response;
   - do not start Docker mutation.
5. If approved or unprotected:
   - acquire existing project deploy lock;
   - build with selected env vars;
   - run/update the selected runtime environment;
   - write deploy log with environment id.

Container/runtime naming:

- production keeps current naming as compatibility baseline.
- staging/development include an environment suffix.
- managed service containers should remain shared in v0.2.0 unless explicitly
  provisioned per environment.

Ports:

- production uses existing range.
- staging/development use distinct ranges or the existing policy range system
  expanded to three keys.
- port allocation must consider all runtime environments.

Routes:

- production uses current public route.
- staging/development should default to internal or explicitly exposed route,
  depending on current web-server capability.
- If exposed, route naming must include the environment key.

Rollback:

- rollback targets the selected environment's previous image/tag.
- production rollback follows the same protection policy as production deploy.

Compose:

- v0.2.0 minimum: compose deploys can target production only unless staging
  support is implemented and tested.
- If compose staging is included, all child service runtime environments must
  share the same project environment key.

### MCP Contract

Affected composites:

- `openlander_deploy`
- `openlander_service`
- `openlander_project`
- `openlander_monitor` for status/diagnostics where relevant

Inputs:

- Add optional `environment_key` to actions that mutate or inspect a deploy
  environment.
- Valid keys in v0.2.0: `production`, `staging`, `development`.
- Default omitted key to `production` for compatibility.

Responses:

- Include:
  - `environment_key`
  - `project_environment_id`
  - `environment_id` where runtime environment exists
- Use only:
  - `status_call`
  - `diagnostic_call`
  - `suggested_call`
  - `poll_call`
- Protected production deploy returns:
  - `status: 'pending_approval'`
  - action run id
  - `poll_call` to check approval/action status
  - `_agent_guidance.next_steps` telling the agent to wait for approval

Validation:

- Unknown environment key -> scoped error with valid keys.
- Protected production without approval -> pending response, not failure.
- Semantic-invalid combinations should not echo the invalid call as
  `suggested_call`.
- `deploy_app(target_project_id, expose=true)` remains blocked unless already
  unblocked before v0.2.

Compatibility:

- Do not remove old action names in v0.2.0.
- If adding service-aligned aliases, keep legacy project-named operations and
  snapshot tests.

### Frontend Spec

Pages/components likely affected:

- `ProjectView`
- `ServiceDetailV2`
- deploy modal/terminal components
- env var/settings components
- activity/deploy history surfaces
- MCP/approval status surfaces if they show pending action runs

UX model:

- Project page has an environment segmented control or tabs:
  `Production`, `Staging`, `Development`.
- Service detail header shows:
  - service name;
  - active environment;
  - runtime status;
  - last deploy;
  - public/internal URL;
  - protection badge if active environment is protected.
- Deploy button opens with environment selection.
- If production requires approval, confirmation copy states that approval is
  required before the deploy starts.
- Pending approval appears in a compact, actionable panel.

Environment variables:

- Show value source:
  - group shared;
  - service override;
  - environment override.
- Editing environment-specific value requires the active environment to be
  explicit.
- Never silently write production env vars while another environment is active.

Topology:

- Show environment filter.
- Managed services appear shared unless per-environment instances are later
  introduced.
- Service connections should make it clear whether the connection is shared or
  environment-scoped.

i18n:

- All new strings use `t()`.
- Update `web/src/i18n/en.ts` and `web/src/i18n/ko.ts` together during
  implementation.

Design constraints:

- This is an operational UI, not a landing page.
- Avoid big marketing-style hero sections.
- Prefer dense, scannable controls and status chips.
- Keep environment controls stable in width so switching state does not cause
  layout shift.

## Release And Test Plan

### Unit/Contract Tests

Add tests for:

- project environment repo canonical creation and uniqueness;
- migration backfill from existing production/development rows;
- env var inheritance and selected environment resolution;
- deploy policy decisions;
- approval request creation and durable pending state;
- MCP schemas and response contracts;
- deploy plan round-trip of environment identity;
- deploy lock remains project-scoped;
- rollback targets selected environment;
- topology/status/log filters include environment identity;
- no 0.2 AI/Ops autonomous path is started by environment policy work.

### Integration Tests

Add focused integration coverage:

- create project -> canonical environments exist;
- create service -> production runtime environment exists or is ensured on
  first deploy;
- staging deploy does not mutate production runtime row;
- production deploy requiring approval does not start Docker mutation before
  approval;
- after approval, deploy proceeds and logs carry production environment id;
- rollback production requires approval;
- MCP agent flow:
  `create_deploy_plan(environment_key='staging')` ->
  `execute_deploy_plan` ->
  `get_deploy_status`.

### E2E Quality Gate

Default fast lane:

- staging deploy path with a minimal Git or image fixture;
- production protected approval path with mocked/lightweight runtime where
  possible;
- env var override visible in deployed output or deploy logs.

Slow lane:

- Docker-backed production approval + deploy;
- managed Postgres/Redis connection under selected environment;
- compose environment path only if compose staging is in v0.2.0 scope.

### Release Gate

Before v0.2.0 RC:

- `npm run typecheck`
- `npm run lint`
- `npm test`
- relevant E2E quality gate
- migration dry-run on representative pre-v0.2 DB
- fresh-VPS cold-agent dry-run:
  install -> token -> create project -> staging deploy -> production approval
  -> production deploy -> logs/status/topology -> rollback policy check.

## Future Roadmap Integration

### v0.2.1 - Private Runtime Inputs

Builds on environment policy by letting each environment select registry
credentials and private image auth.

### v0.2.2 - Notifications And Approval Delivery

Builds on durable approvals by sending production approval requests to Slack or
Discord.

### v0.2.3 - Update Awareness

Scope:

- server-side check for latest GitHub Release;
- UI banner/badge when a newer version is available;
- release notes link;
- exact recommended update command;
- opt-out for outbound version checks.

Non-goal:

- no update execution from the UI.

### v0.3.0 - Guided Self-Update

Scope:

- detect install shape;
- preflight Docker/compose/permissions/DB backup;
- "Update now" button for supported Docker Compose installs;
- job log and progress;
- rollback path before irreversible migrations.

This should require production policy/approval primitives from v0.2 so a
control-plane update cannot happen as an unreviewed background action.

### v0.3.x - Internal AI Ops Re-enable

Only after:

- protected environments exist;
- action runs are durable;
- AI cannot bypass production policy;
- regression tests prove dormant 0.1 guardrails remain closed unless the whole
  0.2/0.3 product surface is intentionally restored.

### v0.4.x - Runtime Backend Expansion

Only after:

- environment-aware deploy model is stable;
- Docker backend has contract tests;
- runtime capabilities are modeled explicitly.

Swarm should be the first likely spike because it is closer to the current
single-host Docker model. Kubernetes/k3s should wait until ingress, secret,
volume, log, and rollback abstractions are proven.

## Open Questions

1. Should migrated projects have production approval enabled immediately, or
   should they receive a visible warning with approval disabled to preserve
   compatibility?

   Recommendation: preserve compatibility for existing projects, protect new
   projects by default.

2. Should staging get a public URL by default?

   Recommendation: no. Make staging internal unless the user explicitly exposes
   it, because accidental public staging exposure is a common operations risk.

3. Should custom environments ship in v0.2.0?

   Recommendation: no. Keep schema forward-compatible, but expose only the
   canonical three.

4. Should managed services be shared across environments?

   Recommendation: yes for v0.2.0. Per-environment managed service instances
   are powerful but should be a later explicit feature.

5. Should deploy locks become environment-scoped?

   Recommendation: no for v0.2.0. Keep project locks until environment behavior
   is battle-tested.

6. Should update awareness call GitHub by default?

   Recommendation: yes with an obvious opt-out setting and no telemetry beyond
   the release metadata request.

## Acceptance Criteria

v0.2.0 is complete when:

- every project has production, staging, and development definitions;
- every deploy/redeploy/rollback can target an environment explicitly;
- omitted environment remains backward-compatible with production;
- staging deploy does not mutate production runtime state;
- production deploy can require durable approval;
- MCP agents receive environment-aware status and poll calls;
- UI clearly shows active environment, protection state, last deploy, and
  pending approval;
- env var resolution is predictable and test-covered;
- migration preserves existing deploy logs/env vars/runtime rows;
- release gate proves both unprotected staging and protected production paths.
