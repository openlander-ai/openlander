# OpenLander v0.2 Roadmap

Date: 2026-06-02
Status: internal planning
Baseline: public v0.1.9 stabilization work, before v0.1.9 tag
Parent roadmap: `.omc/roadmap/openlander-product-roadmap.md`

## Product Thesis

OpenLander v0.1 proves the core loop:

1. Deploy from Git or image.
2. Expose runtime status, logs, health, topology, and deploy diagnostics.
3. Let external MCP-capable agents inspect and operate explicitly.
4. Keep destructive operations deterministic and policy-gated.

The next product step should not be Kubernetes, Docker Swarm, or built-in
autonomous AI remediation. Those are larger surface areas that become safer only
after OpenLander can distinguish production from staging, apply policy to
protected operations, and show humans exactly what will change.

v0.2 is therefore defined as:

> Safe Production Operations: first-class environments, deploy policy, and
> approval-aware agent workflows.

## Architecture Position

v0.2 starts from the current post-split model:

- `projects` is the group boundary.
- `services` is the deployable/managed runtime boundary.
- `environments` is still service-runtime state, not yet a full project-level
  policy model.
- Docker is behind a runtime facade in several paths, but Docker remains the
  only supported backend.

This means the next step is not another broad Project/Service refactor and not
a new runtime backend. The missing product layer is environment policy: the
same service needs a clear production/staging/development target before AI Ops,
Swarm, Kubernetes, or self-update can safely mutate anything.

## Roadmap Order

### v0.2.0 - Safe Production Operations

Primary outcome: users can run a service through `dev`, `staging`, and `prod`
without giving an agent unrestricted production power.

Scope:

- First-class project environments: `production`, `staging`, `development`.
- Environment-scoped env vars and secret references.
- Environment-aware deploy plans, deploy status, logs, topology, and rollback.
- Protected environment policy: production deploys can require human approval.
- MCP responses include enough environment identity for follow-up calls.
- Web UI shows environment state clearly on Project and Service detail pages.
- Release gate includes at least one environment-aware deploy and approval path.

Explicit non-goals:

- No built-in autonomous AI remediation.
- No Kubernetes or Swarm runtime.
- No one-click platform self-update.
- No broad notification center, beyond event hooks needed by approvals.
- No schema-breaking public MCP rename unless compatibility aliases are present.

### v0.2.1 - Private Runtime Inputs

Primary outcome: real teams can deploy private artifacts, not only public repos
or public images.

Scope:

- Private container registry auth for generic OCI registry credentials.
- Follow-up adapters for GHCR, ECR, and Google Artifact Registry.
- Per-environment registry credential selection.
- Deploy-plan validation that distinguishes repo auth from image auth.

### v0.2.2 - Notifications and Approval Delivery

Primary outcome: production changes and failures reach the operator outside the
browser.

Scope:

- Slack and Discord webhook notifications for deploy, approval, health, and
  rollback events.
- Notification templates that include project, service, environment, actor, and
  action links.
- Approval notification links that land on the relevant pending approval view.

### v0.2.3 - Update Awareness

Primary outcome: self-hosted operators know when a newer OpenLander version
exists without reading GitHub manually.

Scope:

- Server-side latest-version check against GitHub Releases.
- UI update banner or badge when `latest > VERSION`.
- Release notes link and exact recommended update command.
- Opt-out setting for installations that do not want outbound checks.

Non-goal:

- The button does not run the update yet. It only tells the user what version is
  available and how to update safely.

### v0.3.0 - Guided Self-Update

Primary outcome: self-hosted operators can update from the UI when the install
shape is known and recoverable.

Scope:

- Preflight: detect install mode, current image/tag, compose file, DB backup
  capability, and write permissions.
- "Update now" button for supported Docker Compose runtime installs.
- Mandatory DB backup before migration.
- Update job status, logs, and failure recovery instructions.
- Rollback path for image update failures before migrations complete.

Why not v0.2.0:

- Self-update touches the running control plane, database migrations, Docker
  Compose state, and possibly root-owned installer state. It is valuable, but it
  should be built after production policy and approval primitives exist.

### v0.3.x - Internal AI Ops Re-enable

Primary outcome: OpenLander can recommend and optionally perform incident
response inside explicit policy.

Required prerequisites:

- v0.2 environment policy and approval gates.
- Durable action run records.
- Clear incident and diagnostic surfaces.
- Regression tests that prove AI Ops cannot bypass protected environments.

Initial scope:

- Suggested remediation only.
- Approval-required destructive actions.
- No silent autonomous production mutation.

### v0.4.x - Runtime Backend Expansion

Primary outcome: prepare for Swarm or Kubernetes without leaking Docker-specific
semantics through the product surface.

Prerequisites:

- Environment-aware deploy model.
- Runtime backend contract tests.
- Clear split between build, workload, network, ingress, secret, volume, logs,
  stats, and rollback capabilities.

Likely sequence:

1. Tighten `RuntimeBackend` into a contract with fake backend tests.
2. Add runtime capability detection and feature flags.
3. Spike Docker Swarm for single-host-to-small-cluster continuity.
4. Spike Kubernetes or k3s only after workload and ingress abstractions are
   proven.

## Strategic Decisions

- v0.2 optimizes for trust, not breadth.
- Production deploy safety comes before internal AI automation.
- Environment and policy concepts should be shared by web, REST, MCP, and
  future internal AI Ops.
- Docker remains the only supported runtime in v0.2.
- Runtime abstraction work should continue behind tests, but no Swarm/Kubernetes
  user-facing promise should be made until v0.4 planning.

## Success Criteria

v0.2 is successful when:

- A user can deploy the same service to staging and production without confusing
  the two.
- Production deploys can require approval, including agent-triggered deploys.
- MCP agents can target an environment explicitly and recover from validation
  errors without guessing.
- The UI makes current environment, last deploy, pending approval, and rollback
  target obvious.
- The release gate proves a protected production path and an unprotected staging
  path.
