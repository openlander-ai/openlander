## 미션 1: 자동 재시작 체인 검증

### 목표

앱이 크래시났을 때 OpsAgent가 자동으로 감지 → 재시작 → 헬스체크 → 성공/실패 처리하는 전체 체인 검증.

### 시나리오

**1-A: 일시적 크래시 → 자동 재시작 성공**

```
1. nginx 앱 배포 (qa-ops-restart)
2. 정상 동작 확인
3. docker exec로 nginx 메인 프로세스 kill (kill 1)
4. 관찰:
   - OpsAgent가 크래시 감지하는지 (deploy:crash 이벤트)
   - 자동 재시작 시도하는지
   - 헬스체크 통과하는지
   - 인시던트 생성 → 복구 → 해소 타임라인
5. Operations Center에서 실시간으로 보이는지
6. 프로젝트 Operations 탭에서 인시던트 표시되는지
```

**1-B: 반복 크래시 → 재시작 실패 → 롤백 시도**

```
1. 잘못된 CMD로 앱 배포 (시작 즉시 exit 1)
2. OpsAgent가 재시작 시도 (3회)
3. 3회 실패 후 롤백 시도하는지
4. 롤백 성공/실패 후 인시던트 상태 변경
5. Operations Center에서 전체 과정 추적 가능한지
```

**1-C: 크래시 루프 → 서킷 브레이커 발동**

```
1. 계속 크래시하는 앱 배포
2. OpsAgent 재시작/롤백 반복
3. 24시간 내 5회 실패 → 서킷 브레이커 열리는지
4. 브레이커 열린 후 추가 복구 시도 차단되는지
5. Operations Center에서 서킷 브레이커 상태 표시
6. 수동으로 브레이커 리셋 후 복구 재시도
```

### 확인 항목

- [ ] `deploy:crash` 이벤트 발생
- [ ] OpsAgent 자동 재시작 (auto_restart: true 시)
- [ ] 헬스체크 3회 시도, 90초 대기
- [ ] 성공 시 인시던트 resolved
- [ ] 실패 시 롤백 파이프라인 진입
- [ ] 서킷 브레이커 5회/24h 제한
- [ ] Operations Center 실시간 표시
- [ ] 프로젝트 Operations 탭 인시던트 타임라인

## 미션 2: 캐스케이드 장애 감지

### 목표

상위 서비스(DB) 장애 시 하위 프로젝트들의 연쇄 장애를 OpsAgent가 감지하고, 개별 프로젝트 재시작이 아닌 근본 원인을 식별하는지 검증.

### 시나리오

**2-A: DB 서비스 중지 → 연결된 앱 캐스케이드**

```
1. PostgreSQL 서비스 생성 (qa-ops-db)
2. DB를 사용하는 앱 2개 배포 (qa-ops-app1, qa-ops-app2)
   - DATABASE_URL로 qa-ops-db 참조
3. 두 앱 정상 동작 확인
4. stop_service(qa-ops-db) 실행
5. 관찰:
   - 30초 내 두 앱의 헬스체크 실패
   - OpsAgent가 캐스케이드 감지하는지 (30초 내 2+ 프로젝트 실패)
   - 개별 재시작 대신 근본 원인(DB) 식별
   - 캐스케이드 알림 생성 (critical 심각도)
6. Operations Center에서 캐스케이드 시각화
7. start_service(qa-ops-db) 후 앱들 자동 복구 확인
```

**2-B: Redis 서비스 중지 → 부분 캐스케이드**

```
1. Redis를 사용하는 앱 1개 + 사용하지 않는 앱 1개
2. Redis 중지
3. Redis 사용 앱만 영향받는지 확인
4. OpsAgent가 정확히 영향받는 프로젝트만 식별하는지
```

### 확인 항목

- [ ] 30초 내 2+ 프로젝트 실패 시 캐스케이드 감지
- [ ] 근본 원인(상위 서비스) 식별
- [ ] 개별 프로젝트 자동 재시작 차단 (근본 원인 해결 필요)
- [ ] 캐스케이드 알림에 영향받는 프로젝트 목록 포함
- [ ] 근본 원인 해결 후 하위 프로젝트 자동 복구

## 미션 3: 빌드 실패 자동 복구 (레시피 + LLM)

### 목표

빌드 실패 시 레시피 패턴 매칭 → 자동 수정 → 재배포, 또는 LLM 진단 → 수정 제안 → 승인 후 재배포 체인 검증.

### 시나리오

**3-A: 레시피 매칭 — 알려진 빌드 에러**

```
1. node-gyp 빌드 실패하는 Dockerfile 준비
   (예: python3/make 없이 native module 빌드)
2. 배포 시도 → 빌드 실패
3. 관찰:
   - auto-recovery가 레시피 매칭하는지
   - Dockerfile 자동 패치 (빌드 도구 추가)
   - 자동 재배포 시도
   - 성공/실패 후 학습 패턴 DB 저장
4. Operations Center에서 "레시피 기반 복구" 표시
```

**3-B: LLM 진단 — 알 수 없는 빌드 에러**

```
1. 레시피에 없는 독특한 빌드 에러 유발
2. 배포 시도 → 빌드 실패
3. 관찰:
   - 레시피 매칭 실패 → LLM 분석 진입
   - LLM이 에러 분석 + 수정 제안
   - 위험한 작업이면 승인 게이트 동작
   - 웹 UI에서 승인 요청 표시되는지
   - 승인 후 수정 적용 + 재배포
4. 승인 거부 시 graceful 실패 확인
```

**3-C: 복구 실패 후 에스컬레이션**

```
1. 복구 불가능한 빌드 에러 (예: 존재하지 않는 base image)
2. 레시피 실패 → LLM 실패 → 복구 불가
3. recovery:exhausted 이벤트 발생 확인
4. 에스컬레이션 알림 생성
5. Operations Center에서 "사람의 개입 필요" 표시
```

### 확인 항목

- [ ] 25+ 레시피 중 적어도 3개 매칭 테스트
- [ ] LLM 기반 진단 동작 (모델 설정 필요)
- [ ] 승인 게이트 동작 (웹 UI에서 approve/reject)
- [ ] 학습 패턴 DB 저장 후 재사용
- [ ] 복구 불가 시 에스컬레이션
- [ ] LLM rate limit 동작 (시간당 3회/프로젝트, 20회/전체)

## 미션 4: 리소스 모니터링 자동 대응

### 목표

디스크/메모리 임계값 초과 시 OpsAgent의 자동 정리 및 알림 검증.

### 시나리오

**4-A: 디스크 사용량 임계값 초과**

```
1. 현재 디스크 사용량 확인 (86%)
2. 임계값을 현재 사용량보다 낮게 설정 (예: 85%)
3. 관찰:
   - OpsAgent가 디스크 경고 감지
   - auto_cleanup 동작: dangling images, build cache 정리
   - 정리 후 사용량 변화
   - 10분 쿨다운 후 재검사
4. Operations Center에서 정리 이력 표시
```

**4-B: 컨테이너 OOM Kill**

```
1. 메모리 제한 설정된 앱 배포
2. 메모리 초과 유발
3. OpsAgent가 OOM Kill 감지하는지
4. 알림 생성 여부
5. 재시작 후 동일 문제 반복 시 진단 제공 여부
```

### 확인 항목

- [ ] 디스크 80% 초과 시 자동 정리
- [ ] 정리 쿨다운 10분
- [ ] 빌드 진행 중이면 정리 안 함
- [ ] running 프로젝트에 영향 없음 (이전 QA에서 확인됨)

## 미션 5: 포스트모텀 자동 생성

### 목표

인시던트 발생 → 복구/에스컬레이션 후 포스트모텀 리포트가 자동 생성되는지 검증.

### 시나리오

```
1. 미션 1-B 실행 (크래시 → 재시작 실패 → 롤백)
2. 인시던트 종료 후 포스트모텀 생성 확인
3. 포스트모텀 내용 검증:
   - 타임라인 테이블 (감지 → 조치 → 결과)
   - 근본 원인 분석
   - 기여 요인
   - 재발 방지 조치
   - 24시간 체크리스트
4. 한국어/영어 로케일 확인
5. 크리덴셜 마스킹 확인 (DB URL, API 키 등)
6. Operations Center에서 포스트모텀 조회 가능한지
```

### 확인 항목

- [ ] 포스트모텀 자동 생성 (복구 성공/실패 모두)
- [ ] SRE 수준의 구조화된 리포트
- [ ] 크리덴셜 자동 마스킹

## 미션 6: 일일 다이제스트

### 목표

OpsAgent의 매일 09:00 자동 다이제스트가 정확한 정보를 포함하는지 검증.

### 시나리오

```
1. 다이제스트 시간을 현재 시각 +2분으로 변경
2. 미션 1~4에서 발생한 인시던트가 있는 상태에서 다이제스트 트리거
3. 다이제스트 내용 검증:
   - 프로젝트 수 (running/stopped/error)
   - 24시간 인시던트 요약 (total, auto-resolved, escalated)
   - 리소스 사용량 (CPU, memory, disk %)
   - 열린 서킷 브레이커 목록
4. 알림 채널로 발송 확인 (설정된 경우)
```

### 확인 항목

- [ ] 예약 시간에 다이제스트 생성
- [ ] 프로젝트/인시던트/리소스 수치 정확
- [ ] 서킷 브레이커 있으면 severity: warning

## 오픈클로 실행 방법

### 에이전트 설정

```bash
# 3개 에이전트로 병렬 실행
openclaw agent --local --agent qa1 --timeout 3600 -m "미션 1-3"
openclaw agent --local --agent qa2 --timeout 3600 -m "미션 4-6"
openclaw agent --local --agent live --timeout 3600 -m "미션 7 (웹 UI 관찰)"
```

### 주의사항

- `exec-approvals.json`의 `defaults`에 자동 승인 설정 필요
- 미션 3-B (LLM 진단)은 LLM 설정이 되어있어야 함
- 미션 2 (캐스케이드)는 서비스 2개 + 앱 2개 필요 → 리소스 확인
- 프로젝트 접두사: `qa-ops-` (이전 QA와 구분)
- 결과 기록: `docs/launchpad/qa-ops-findings.md`

### 성공 기준

- 미션 1-6 각각 80% 이상 항목 통과
- Operations Center에서 전체 과정 실시간 추적 가능
