# When AI Agents Touch the Real World: A 6-Layer Safety Model

> 15,000 LLM 호출 사고에서 배운 것.
> 자율 AI 에이전트가 현실 세계를 조작할 때 필요한 안전 모델.

---

## 하루에 15,000번의 LLM 호출

셀프 호스팅 배포 플랫폼을 만들고 있다. AI가 서버 장애를 감지하면 자동으로 원인을 분석하고, 복구하고, 보고서를 쓴다. 코딩 에이전트가 코드를 고치듯, 우리 에이전트는 인프라를 고친다.

어느 날 AI usage 대시보드를 열었더니, 하루 만에 LLM 호출이 15,000건을 넘기고 있었다.

원인은 단순했다. 이미 멈춘 프로젝트 3개의 컨테이너가 아직 살아있었다. 10초마다 컨테이너가 재시작되고, 그때마다 3개의 독립적인 AI 컴포넌트가 각각 반응했다. 자동 복구 에이전트, 운영 에이전트, 사후 분석 생성기. 서로의 존재를 모른 채 각자 LLM을 호출했다.

6시간 동안 6번 패치했다. 매번 다른 구멍이 터졌다.

```
10:49  stopped/archived 프로젝트 스킵 → error 상태가 빠져나감
11:24  guard 3곳 추가 → PostmortemGenerator에는 안 넣음
12:10  blacklist를 whitelist로 전환 → 이미 돌고 있는 건 안 멈춤
12:17  PostmortemGenerator 통째로 비활성화 → 기능 자체를 잃음
```

이건 코드 버그가 아니었다. **아키텍처 결함**이었다.

---

## 코딩 에이전트는 왜 이런 문제가 없을까

Cursor, Claude Code 같은 코딩 에이전트를 생각해보자. 이들은 놀라울 정도로 자유롭게 동작한다. 파일을 읽고, 코드를 고치고, 터미널을 실행한다. 실수하면? `git checkout`. 끝.

우리 에이전트는 달랐다. Docker 컨테이너를 재시작하고, 환경 변수를 바꾸고, 이미지를 롤백한다. 실수하면? **사용자의 서비스가 죽는다.**

코딩 에이전트가 자유로운 이유는 결과를 되돌릴 수 있기 때문이다. 인프라 에이전트에 그 자유를 주면 하루 만에 15,000번 호출이 발생한다.

---

## 하나의 원칙

사고를 분석하면서 하나의 원칙에 도달했다:

> **에이전트의 자율성은 결과의 되돌림 가능성에 반비례하여 제한되어야 한다.**

```
되돌리기 쉬움                                    되돌리기 불가능
     │                                                │
     ▼                                                ▼
  코딩 에이전트    인프라 에이전트    금융 에이전트    의료/자율주행
  (git checkout)   (rollback 가능)    (돈 이체)       (인명)
     │                  │                │               │
  자율성 높음       자율성 중간      자율성 낮음     자율성 최소
```

코딩 에이전트에는 "실행 → 확인 → 되돌리기" 루프만으로 충분하다. 하지만 결과를 되돌리기 어려운 도메인에서는 **실행 전에** 안전장치가 필요하다.

## 6-Layer Safety Model

15,000번의 호출과 6번의 패치 끝에, 우리는 6개의 안전 레이어를 발견했다. 각 레이어는 사고를 겪으면서 "이것도 필요했구나"라고 깨달은 것들이다.

```
  ┌──────────────────────────────────────────────┐
  │  Layer 6: Visibility                          │
  │  "AI가 뭘 하고 있는지 사람이 볼 수 있는가?"   │
  ├──────────────────────────────────────────────┤
  │  Layer 5: Budget Enforcement                  │
  │  "허용된 자원(비용/시간/횟수) 내인가?"         │
  ├──────────────────────────────────────────────┤
  │  Layer 4: Circuit Breaker                     │
  │  "반복 실패 중이 아닌가?"                      │
  ├──────────────────────────────────────────────┤
  │  Layer 3: Operator Suppression                │
  │  "사람의 의도적 행동과 충돌하지 않는가?"       │
  ├──────────────────────────────────────────────┤
  │  Layer 2: Status Ownership                    │
  │  "이 상태를 변경할 권한이 있는가?"             │
  ├──────────────────────────────────────────────┤
  │  Layer 1: Eligibility Gate                    │
  │  "행동해도 되는 상황인가?"                     │
  └──────────────────────────────────────────────┘

   ── 모든 layer를 통과해야 에이전트가 현실 세계에 손을 댈 수 있다 ──
```

### Layer 1: Eligibility Gate

**"이 상황에서 행동해도 되는가?"**

가장 기본적인 관문. 에이전트가 행동하기 전에 전제 조건을 확인한다.

우리 사고에서: 프로젝트가 `error` 상태인데 복구 에이전트가 동작했다. guard가 `stopped`와 `archived`만 차단하고 `error`는 빠뜨렸다. blacklist 방식의 한계.

**교훈**: blacklist("이 상태에서는 하지 마라")가 아니라 whitelist("이 상태에서만 해라")로 구현해야 한다. 새로운 상태가 추가될 때 자동으로 차단된다.

```
❌  if (status === 'stopped' || status === 'archived') return;  // error가 빠짐
✅  if (status !== 'running') return;                            // running만 허용
```

### Layer 2: Status Ownership

**"누가 시스템 상태를 변경할 권한이 있는가?"**

우리 사고에서: Health Monitor가 crash를 감지하면 프로젝트 상태를 `error`로 바꿨다. 그런데 Recovery Coordinator도 같은 상태를 바꿔야 했다. 둘이 동시에 상태를 건드리니 race condition이 발생했다.

더 큰 문제: Health Monitor가 상태를 `error`로 바꾸면, Coordinator의 Eligibility Gate가 "running이 아니네?"로 판단하고 복구를 거부했다. **감지 시스템이 복구 시스템을 차단하는 셀프 블록.**

**교훈**: 감지(Detection)와 행동(Action)의 권한을 분리해야 한다. 감지하는 쪽은 이벤트만 발행하고, 상태 변경은 행동하는 쪽만 할 수 있어야 한다.

### Layer 3: Operator Suppression

**"사람이 의도적으로 한 행동을 AI가 되돌리고 있지 않은가?"**

우리 사고에서: 관리자가 프로젝트를 멈추면, Docker 컨테이너가 `die` 이벤트를 발생시켰다. 복구 에이전트는 "컨테이너가 죽었다!"로 판단하고 즉시 복구를 시도했다. 관리자가 의도적으로 멈춘 건데.

**교훈**: 사람의 행동과 시스템 장애를 구분해야 한다. 관리자가 stop/restart/deploy를 실행하면, 일정 시간 동안 해당 대상에 대한 자동 복구를 억제해야 한다.

### Layer 4: Circuit Breaker

**"같은 실패를 반복하고 있지 않은가?"**

우리 사고에서: 복구 에이전트가 실패해도 10초 후 또 시도했다. PostmortemGenerator는 재시도 제한이 아예 없었다. 결과: 같은 실패를 15,000번 반복.

**교훈**: N번 실패하면 더 이상 시도하지 않아야 한다. 그리고 이 상태는 사람이 명시적으로 리셋할 때까지 유지되어야 한다. 자동으로 풀리면 다시 루프에 빠진다.

### Layer 5: Budget Enforcement

**"허용된 자원 내에서 동작하고 있는가?"**

우리 사고에서: LLM 호출에 글로벌 비용 상한이 없었다. 개별 컴포넌트마다 재시도 제한은 있었지만(3회, 5회), 전체 시스템 수준의 예산은 없었다. 3개 컴포넌트 × 각자의 한도 = 예상보다 훨씬 많은 호출.

**교훈**: 개별 컴포넌트의 제한과 별도로, 전체 시스템 수준의 예산 한도가 필요하다. "시간당 LLM 10회" 같은 단순한 규칙이면 충분하다.

### Layer 6: Visibility

**"AI가 뭘 하고 있는지 사람이 볼 수 있는가?"**

우리 사고에서: 15,000번 호출이 발생하는 동안 UI에서 알 수 있는 방법이 없었다. AI usage 대시보드는 10초마다 폴링했고, Notification에 AI 관련 알림은 없었다. agent:event는 발행됐지만 아무 UI도 받지 않았다.

결과: 사고를 감지하기까지 수 시간이 걸렸다. 실시간 비용 카운터가 있었다면 수 분 내에 알 수 있었다.

**교훈**: AI가 비용을 쓰는 행위는 반드시 실시간으로 사람에게 보여야 한다. "AI가 백그라운드에서 돈을 쓰고 있는데 사용자가 모른다"는 기능이 아니라 사고다.

## 도메인별 적용

이 모델은 인프라에 국한되지 않는다. AI 에이전트가 현실 세계에 영향을 미치는 모든 곳에 적용된다.

| 도메인        | 그 도메인의 "15K 호출 사고"                 | 필요한 Layer |
| ------------- | ------------------------------------------- | ------------ |
| 인프라 운영   | 복구 에이전트 무한 루프 → 비용 폭주         | 전부         |
| 금융 트레이딩 | 봇이 무한 매수/매도 반복 → 계좌 증발        | 1,3,4,5,6    |
| 고객 서비스   | 환불 봇이 모든 요청 자동 승인 → 손실        | 1,2,3,5      |
| 스마트 팩토리 | AI가 기계 설정 반복 변경 → 불량품 대량 생산 | 1,2,3,4,6    |
| IoT/스마트홈  | AI가 에어컨을 끝없이 on/off → 전기세 폭탄   | 1,3,4,5      |
| 의료          | AI 처방 에이전트가 동일 약 반복 처방        | 전부 + α     |

결과의 되돌림이 어려울수록 더 많은 레이어가 필요하다.

## 코딩 에이전트가 가르쳐주지 않는 것

2025년, 코딩 에이전트가 "AI 에이전트"의 기준을 만들었다. Cursor, Claude Code, Devin은 놀라운 자율성을 보여줬다. 자연스럽게 "이 패턴을 다른 도메인에도 적용하자"는 흐름이 생겼다.

하지만 코딩 에이전트의 성공은 특수한 조건 위에 있었다:

```
코딩 에이전트의 특권:
  ✅ 즉각 검증 (코드 실행하면 맞는지 바로 앎)
  ✅ 완벽한 되돌리기 (git checkout)
  ✅ 격리된 환경 (로컬 파일시스템)
  ✅ 낮은 실패 비용 (컴파일 에러 ≠ 서비스 다운)
  ✅ 명확한 성공 기준 (테스트 통과)
```

이 조건들이 없는 도메인에 코딩 에이전트의 자율성 수준을 그대로 적용하면, 우리가 겪은 일이 발생한다. 15,000번의 LLM 호출, 6번의 실패한 패치, 그리고 아키텍처 전면 재설계.

**코딩 에이전트에서 배울 것**: tool 사용, 피드백 루프, 자율적 문제 해결.
**코딩 에이전트에서 배우면 안 되는 것**: 안전장치 없이도 괜찮다는 전제.

---

## 결론: 에이전트 시대의 안전장치

2026년, AI 에이전트는 코드를 넘어 인프라, 금융, 운영, 고객 서비스로 확장되고 있다. 이 확장에서 가장 위험한 가정은 "코딩 에이전트처럼 만들면 되겠지"이다.

코딩 에이전트는 `git checkout`이 있기 때문에 자유로운 거다. 그 안전망이 없는 도메인에서는, 에이전트가 행동하기 전에 물어야 할 6가지 질문이 있다:

```
1. 행동해도 되는 상황인가?          (Eligibility Gate)
2. 이 상태를 변경할 권한이 있는가?   (Status Ownership)
3. 사람의 의도와 충돌하지 않는가?    (Operator Suppression)
4. 반복 실패 중이 아닌가?           (Circuit Breaker)
5. 허용된 자원 내인가?              (Budget Enforcement)
6. 사람이 관찰 가능한가?            (Visibility)
```

이 6가지를 전부 통과해야 에이전트가 현실 세계에 손을 댈 수 있다.

우리는 이걸 15,000번의 LLM 호출로 배웠다. 당신은 이 글로 배웠으면 좋겠다.
