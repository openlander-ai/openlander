# v1.0.0 — AI Co-pilot (AI 통합 경험)

> **⚠ Historical — frozen 2026-04-23 (pre-1.0 launch).**
> This file captures an earlier AI co-pilot concept; frontend inline AI cards were replaced by the chat pattern (DEC-041), and the shipped 1.0 AI surface is described in the release notes.
> Current state: `docs/RELEASE-NOTES-1.0.md`, `docs/wiki/AI-Auto-Recovery.md`.
> Kept in place because other planning docs still link here.

> **⚠️ 부분 대체**: 프론트엔드 인라인 AI 카드(F-H)는 DEC-041에서 챗봇 패턴으로 전환됨.
> 백엔드 기능(F-A~F-G)은 유효. 새 웹 UI 설계: `docs/planning/release/v1.0.0-web-ui-vision.md`

## 개요

- **한 줄 요약**: AI를 에러 시 소방관에서, 배포 전체 라이프사이클의 "조용한 부조종사"로 전환
- **핵심 문제**: AI가 에러 발생 시에만 존재감이 있고, 성공/평상시에는 완전히 부재
- **해결 방법**: 7개 기능 + 1개 UX 개편을 통해 배포 → 감시 → 감지 → 복구 → 학습 전 과정에 AI 존재감 확보
- **PM 결정**: 안 B (인라인 AI) 채택, UI/UX 디자이너 협업 범위 = AI 통합 UX 전체

## 설계 원칙

```
1. 컨텍스트 내 존재 — 별도 페이지/챗봇 ❌, 사용자가 보고 있는 곳에서 인라인
2. 비례적 반응 — 성공 = 한 줄, 주의 = 카드, 장애 = 풀 분석
3. 옵트아웃 가능 — 모든 AI 표시는 닫기/무시 가능 (Non-blocking)
4. 설명 가능 — AI 행동에는 항상 "왜"가 함께 표시
5. 신뢰감 > 화려함 — 이모지/애니메이션 최소화, 정확성 우선
```

## 기능별 상세

### F-A: AI 자동 복구 (Auto-Recovery) — ✅ 구현 완료

- **AS-IS**: deploy:failed → 2초 후 agent.chatStream → 복구 시도 (최대 3회)
- **TO-BE**: 동일 (변경 없음)
- **비고**: 이미 핵심 기능으로 동작 중. 프론트엔드 존재감만 강화 (F-H에서 처리)

### F-B: 자동 장애 리포트 (Auto Incident Report) — ✅ 백엔드 구현 완료

- **AS-IS**: 복구 성공/실패 시 아무 알림 없음
- **TO-BE**: recovery:success → Slack/Discord/Telegram에 장애 복구 리포트 자동 전송
- **구현 방향**:
  - `src/monitor/incident-reporter.ts` — 이벤트 구독 → 메시지 포맷 → broadcast
  - recovery:start 시 인시던트 상태맵 생성, success/exhausted 시 리포트 생성
- **수락기준**:
  - [ ] recovery:success 발생 시 연결된 채널에 한국어 리포트 전송
  - [ ] recovery:exhausted 발생 시 "수동 확인 필요" 리포트 전송
  - [ ] 채널 미연결 시 에러 없이 스킵
  - [ ] 프론트엔드: 타임라인에 RecoveryReportCard 표시
- **프론트엔드**: MCP-first 전환으로 프론트엔드 UI 스코프 아웃 (DEC-037). MCP 경유로 결과 조회.
  - ~~타임라인에 "장애 복구 완료" / "장애 복구 실패" 요약 카드 표시~~
  - ~~카드에 시도 횟수, 소요 시간, 원인 요약 포함~~

### F-C: 롤백 자동 제안 (Auto Rollback Suggestion) — ✅ 백엔드 구현 완료

- **AS-IS**: 배포 후 헬스체크 실패해도 아무 행동 없음 (사용자가 수동으로 롤백)
- **TO-BE**: 배포 성공 후 60초간 헬스 감시 → 연속 3회 실패 → AI가 롤백 제안
- **구현 방향**:
  - `src/monitor/rollback-watcher.ts` — deploy:success 구독 → 60초간 monitor:healthcheck 감시
  - 연속 3회 unhealthy → eventBus.emit('rollback:suggested', { projectId, reason })
  - agent에게 메시지 전달 → ask_user_question으로 "롤백할까요?" 확인
- **수락기준**:
  - [ ] deploy:success 후 60초간 헬스 감시 활성화
  - [ ] 연속 3회 healthcheck 실패 시 rollback:suggested 이벤트 발생
  - [ ] agent가 사용자에게 "이전 버전으로 롤백할까요?" 질문
  - [ ] 사용자 승인 시 rollback_project 도구 호출
  - [ ] 승인/거부 결과를 타임라인에 표시
  - [ ] 정상 배포 시 (헬스체크 통과) 아무 행동 없음
- **프론트엔드**: MCP-first 전환으로 프론트엔드 UI 스코프 아웃 (DEC-037). MCP 경유로 대체.
  - ~~타임라인에 "AI가 롤백을 제안합니다" 카드 — [확인] [무시] 버튼~~

### F-E: 포스트모템 자동 생성 (Auto Postmortem Generation) — ✅ 구현 완료

- **AS-IS**: 장애 발생 → 복구 후 기록 없음
- **TO-BE**: recovery:success 또는 recovery:exhausted → 마크다운 포스트모템 자동 생성
- **구현 방향**:
  - `src/monitor/postmortem.ts` — LLM에게 타임라인 데이터 제공 → 구조화된 마크다운 반환
  - 입력: deploy_logs(빌드 로그, 에러), chat_history(AI 응답), 타임스탬프
  - 출력: 마크다운 (## 타임라인, ## 근본 원인, ## 수정 내용, ## 예방 조치)
  - DB 저장: deploy_logs 테이블의 metadata 컬럼 또는 별도 컬럼
  - API: GET /api/projects/:id/postmortem/:logId
- **수락기준**:
  - [ ] recovery:success 시 포스트모템 자동 생성
  - [ ] recovery:exhausted 시에도 "미해결" 포스트모템 생성
  - [ ] 마크다운 형식: 타임라인 → 근본 원인 → 수정 내용 → 예방 조치
  - [ ] API로 조회 가능
  - [ ] 타임라인에서 "포스트모템 보기" 링크

### F-F: 시크릿 스캔 → 환경변수 자동 등록 (Secret Scan) — ✅ 백엔드 구현 완료

- **AS-IS**: 코드에 하드코딩된 API 키/DB 비밀번호 → 그대로 배포됨
- **TO-BE**: 빌드 시 코드 스캔 → 하드코딩 시크릿 발견 → "환경변수로 이관할까요?" 제안
- **구현 방향**:
  - `src/pipeline/secret-scan.ts` — 빌드 전 코드 스캔
    - 패턴 매칭: API 키 형식 (sk-_, AKIA_, ghp\_\* 등), DB URL, 고엔트로피 문자열
    - .env, .gitignore, node_modules 제외
    - 결과: `{ file, line, keyName, pattern }[]`
  - clone 후, build 전에 실행
  - 감지 시 → eventBus.emit('secret:detected', { projectId, secrets })
  - agent에게 메시지 → "코드에 시크릿이 노출됨. 환경변수로 이관하세요"
- **수락기준**:
  - [ ] clone 후 소스 코드에서 시크릿 패턴 감지
  - [ ] 감지된 시크릿 목록을 타임라인에 표시
  - [ ] agent가 "환경변수로 이관하세요" 안내
  - [ ] 사용자 승인 시 set_env_vars로 등록
  - [ ] .env, node_modules, .git 디렉토리 제외
  - [ ] 오탐 최소화: 고신뢰 패턴만 (API 키 접두사, AWS 키 형식 등)
- **프론트엔드**: MCP-first 전환으로 프론트엔드 UI 스코프 아웃 (DEC-037). MCP 경유로 대체.

## 디자이너 브리프

### 디자인 대상 7개 영역

**1. 빌드 실패 → AI 인라인 분석 (F-H) — 최우선**

```
현재: 빌드 로그 → 에러 → [별도 그룹] AI Analysis
목표: 빌드 로그 → 에러 → ── 🤖 AI 분석 ── → AI 스트리밍 (같은 흐름)

핵심: 빌드 로그와 AI 분석의 경계가 자연스러워야 함
참고: 안 B — 인라인 (분할 뷰 아님)
```

**2. 대시보드 프로젝트 카드 AI 상태**

```
현재: 상태 뱃지 (Running/Stopped/Failed) 만 표시
목표: AI 한 줄 상태 추가 ("정상 운영 중" / "⚠️ 빌드시간 증가" / "🔄 복구 중")
```

**3. 롤백 제안 카드 (F-C)**

```
Intent Preview 패턴:
"배포 후 헬스체크 3회 연속 실패. 이전 버전으로 롤백할까요?"
[이전 버전 복원] [무시]
```

**4. 환경변수 감지 카드 (F-D)**

```
".env.example에 새 키 3개 발견: API_KEY, DB_URL, REDIS_HOST"
+ 입력 폼 (기존 InputRequestCard 확장 가능)
```

**5. 시크릿 감지 카드 (F-F)**

```
"⚠️ 코드에 시크릿 노출됨"
- src/config.ts:15 — AWS Access Key (AKIA...)
- src/db.ts:8 — Database URL (postgres://...)
[환경변수로 이관] [무시]
```

**6. 포스트모템 카드 (F-E)**

```
"📝 장애 포스트모템 생성됨"
- 근본 원인: dependency 버전 충돌
- AI 수정: package.json 의존성 고정
- 예방 조치: lockfile 커밋 권장
[전체 보기]
```

**7. 성공 인사이트 강화 (F-G)**

```
현재: "✅ 배포 완료. 이상 없음." (InsightCard)
목표: "✅ 배포 완료 (32초). 빌드 시간이 이전 대비 15% 빨라졌습니다."
```

### 디자인 원칙

- 기존 InsightCard, InputRequestCard, DockerfileFixedCard 스타일과 일관성 유지
- 레벨: 🟢 정상(한 줄) → 🟡 주의(카드) → 🔴 장애(풀 패널)
- 모바일 호환 필수 (단일 컬럼 레이아웃)
- 참조 컴포넌트: `web/src/components/timeline/` 디렉토리 전체
