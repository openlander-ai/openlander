# v0.0.11 — Agent Proactivity (에이전트 능동성)

> **상태**: 📋 기획 초안 | **이전 버전**: v0.0.9 Server Awareness (구현 완료)
>
> 이 기능은 OpenLander가 **"서버 상태를 아는 배포 에이전트"**에서 **"서버 상태를 알고, 먼저 말해주는 배포 에이전트"**로 진화하는 핵심 피처다.

---

## 핵심 문제

v0.0.9에서 에이전트가 서버 상태를 "알게" 됐다. 하지만 **묻기 전엔 말하지 않는다**.

```
현재 (수동):
  유저: "서버 상태 알려줘"  → 에이전트: "컨테이너 14개, 포트 12개 사용 중..."
  유저: "배포해줘"           → preflight → 배포

되어야 하는 것 (능동):
  에이전트: "배포 성공했어. 헬스체크 통과, 메모리 정상. 근데 이전 버전 컨테이너가 아직 있어 — 정리할까?"
  에이전트: "ext-postgres가 30분째 CPU 100%인데, 확인해볼래?"
  에이전트: "이 앱은 저번에 포트 10003 썼으니까 같은 포트로 배포할게."
```

**한 줄 요약**: 에이전트가 정보를 수동적으로 제공하는 것에서, **적절한 타이밍에 능동적으로 인사이트를 전달**하는 것으로 전환.

---

## 왜 이게 중요한가

1. **제품 정체성 강화** — "서버 상태를 아는"의 진짜 의미는 아는 것을 **활용**하는 것
2. **"AI다운" 체감** — 유저가 "이건 스크립트가 아니라 에이전트구나" 느끼는 순간
3. **경쟁 차별화** — Coolify/Dokploy에는 AI가 전혀 없음. 능동적 AI는 추격 불가능한 차별점
4. **DevOps 페르소나 핵심 가치** — "알아서 해줘"가 민수의 진짜 니즈

---

## 설계 원칙

### 1. 안전 우선: 관찰만, 실행은 사용자 승인

```
✅ "이전 버전 컨테이너가 있어. 정리할까?"  → 유저 확인 후 실행
❌ "이전 버전 컨테이너를 정리했어."         → 절대 금지
```

에이전트는 **제안**만 한다. 자율 실행은 인프라에서 위험하다 (DEC-001 참조).

### 2. 소음 방지: 보여주되, 귀찮게 하지 않는다

```
좋은 예: 배포 직후 한 번 "헬스체크 OK, 이전 버전 있음" → 끝
나쁜 예: 30초마다 "CPU 12%입니다" "메모리 42%입니다" → 소음
```

**트리거 기반**: 주기적 알림이 아니라, **이벤트 발생 시**에만 능동적으로 말한다.

### 3. 컨텍스트 기억: 과거를 알고 현재를 판단한다

```
첫 배포: "포트 10003을 할당했어."
재배포: "저번에 10003 썼으니까 같은 포트로 갈게."  → 기억 기반 판단
```

## 기능별 상세

### 11-1: Post-Deploy Insight (배포 후 인사이트)

**트리거**: `deploy:success` 이벤트 발생 시

배포 성공 후 에이전트가 자동으로 서버 상태를 점검하고 인사이트를 채팅에 전달한다.

**체크 항목**:

| 항목               | 조건                                      | 메시지 예시                                                           |
| ------------------ | ----------------------------------------- | --------------------------------------------------------------------- |
| 헬스체크           | 배포 후 30초 내 통과                      | `✅ 헬스체크 통과 (응답 200, 2.1초)`                                  |
| 헬스체크 실패      | 30초 내 미통과                            | `⚠️ 헬스체크 아직 미통과. 로그를 확인할까?`                           |
| 이전 버전 컨테이너 | 같은 프로젝트의 이전 이미지 컨테이너 존재 | `💡 이전 버전 (abc123) 컨테이너가 아직 있어. 정리할까?`               |
| 리소스 상태        | 배포 후 메모리 80%+ 도달                  | `⚠️ 배포 후 메모리 사용량이 82%로 올랐어. 주시할게.`                  |
| 빌드 시간 비교     | 이전 빌드 대비 2배+ 느림                  | `📊 빌드 시간 3분 42초 — 저번보다 2배 느려졌어. 캐시 문제일 수 있어.` |

**구현 방향**:

```typescript
// src/pipeline/deploy.ts — deploy:success 이벤트 후
async function postDeployInsight(projectId: string, deployResult: DeployResult): Promise<string[]> {
  const insights: string[] = [];

  // 1. 헬스체크 상태
  const health = await waitForHealthCheck(projectId, 30_000);
  insights.push(
    health.ok
      ? `✅ 헬스체크 통과 (${health.responseTime}ms)`
      : `⚠️ 헬스체크 미통과. 로그를 확인할까?`,
  );

  // 2. 이전 버전 컨테이너
  const staleContainers = await findStaleContainers(projectId);
  if (staleContainers.length > 0) {
    insights.push(`💡 이전 버전 컨테이너 ${staleContainers.length}개가 있어. 정리할까?`);
  }

  // 3. 리소스 변화
  const stats = await getSystemStats();
  if (stats.memory.usedPercent > 80) {
    insights.push(`⚠️ 메모리 ${stats.memory.usedPercent}% 사용 중.`);
  }

  return insights;
}
```

**수락기준**:

- [ ] 배포 성공 후 에이전트가 자동으로 인사이트 메시지를 채팅에 표시한다
- [ ] 헬스체크 결과(통과/미통과)를 포함한다
- [ ] 이전 버전 컨테이너가 있으면 정리를 제안한다 (실행은 유저 승인 필요)
- [ ] 리소스 임계값(메모리 80%+) 초과 시 경고한다
- [ ] 인사이트가 없으면 (모든 것이 정상이면) 간결하게 `✅ 배포 완료. 이상 없음.` 만 표시
- [ ] 배포 실패 시에는 이 기능이 트리거되지 않는다
- [ ] 테스트: 정상 배포, 헬스체크 실패, 이전 버전 존재, 리소스 초과 시나리오

### 11-2: Anomaly Nudge (이상 징후 알림)

**트리거**: 기존 HealthMonitor의 `monitor:healthcheck` / `monitor:inactive` 이벤트

컨테이너가 비정상 상태가 되면, 에이전트가 **채팅에 한 번** 알려준다. 반복 알림은 하지 않는다.

**감지 항목**:

| 이상 징후          | 감지 방법                                 | 메시지                                                        |
| ------------------ | ----------------------------------------- | ------------------------------------------------------------- |
| 컨테이너 크래시    | `state: exited` + `exitCode != 0`         | `🔴 frontend 컨테이너가 크래시했어 (exit code 1). 로그 볼까?` |
| 반복 재시작        | `restartCount > 3` in 10분                | `🔴 api가 10분 내 4번 재시작됐어. 크래시 루프인 것 같아.`     |
| 리소스 포화        | 컨테이너 메모리 90%+ (cgroup limit 기준)  | `⚠️ postgres 컨테이너가 메모리 제한에 근접했어 (92%).`        |
| 디스크 부족        | 호스트 디스크 5GB 미만                    | `⚠️ 디스크 여유 3.2GB. Docker 이미지 정리 제안할까?`          |
| 외부 컨테이너 변화 | v0.0.9 listAllContainers와 이전 스캔 비교 | `📋 외부 컨테이너 변화 감지: grafana가 새로 추가됨.`          |

**소음 방지 규칙**:

1. **동일 이슈는 한 번만 알림** — 같은 컨테이너의 같은 이상 징후는 해결되기 전까지 재알림 안 함
2. **쿨다운 5분** — 한 이슈를 알린 후 최소 5분은 대기
3. **최대 3개/시간** — 시간당 능동 메시지 3개 초과 금지
4. **사용자 묵음 가능** — `이 컨테이너 알림 끄기` 응답 시 해당 건 무시

**구현 방향**:

```typescript
// src/monitor/anomaly.ts — 신규 파일
interface AnomalyState {
  notified: Map<string, number>; // key → last notified timestamp
  hourlyCount: number;
  mutedContainers: Set<string>;
}

async function checkAnomalies(
  containers: AllContainerInfo[],
  previousContainers: AllContainerInfo[],
  stats: SystemStats,
): Promise<AnomalyNudge[]> {
  // ...감지 로직
}
```

**수락기준**:

- [ ] 관리 컨테이너의 크래시, 반복 재시작, 리소스 포화를 감지한다
- [ ] 호스트 디스크 부족(5GB 미만)을 감지한다
- [ ] 외부 컨테이너 추가/제거를 감지한다 (v0.0.9 `listAllContainers` 활용)
- [ ] 동일 이슈 반복 알림 방지 (한 번 알린 건 해결 전까지 재알림 안 함)
- [ ] 시간당 최대 3건 제한
- [ ] 사용자가 특정 컨테이너의 알림을 끌 수 있다
- [ ] 알림 메시지에 **행동 제안** 포함 ("로그 볼까?", "정리할까?")
- [ ] 테스트: 크래시 감지, 반복 재시작, 디스크 부족, 소음 방지 시나리오

### 11-3: Smart Defaults (스마트 기본값)

**트리거**: 배포 요청 시 (`deploy_project` 도구 호출 전)

에이전트가 이전 배포 히스토리를 참고하여 더 나은 기본값을 제안한다.

**시나리오**:

| 상황                | 현재                       | Smart Defaults                                                |
| ------------------- | -------------------------- | ------------------------------------------------------------- |
| 재배포              | 유저가 포트/이름 다시 지정 | "저번에 10003 썼으니까 같은 포트로 할게"                      |
| 환경변수            | 매번 새로 설정             | "저번 배포에서 DB_URL 설정했었어. 같이 적용할까?"             |
| 같은 레포 재배포    | clone부터 다시             | "이 레포 이미 clone 되어있어. pull만 할게."                   |
| 빌드 실패 후 재시도 | 같은 설정으로 재시도       | "저번 빌드 실패 원인이 메모리였어. --memory 옵션 추가해볼까?" |

**구현 방향**:

```typescript
// src/agent/prompts.ts — buildContextSnapshot() 확장
// 기존: 현재 서버 상태만 포함
// 추가: 해당 프로젝트의 배포 히스토리

// 시스템 프롬프트에 주입:
// ## Deployment History for "frontend"
// - Last deployed: 2h ago, port 10003, env: DB_URL=..., BUILD_TIME=2m30s
// - Previous failures: 1 (memory limit, resolved with --memory 4g)
// - Recommended: same port 10003, same env vars, add --memory 4g
```

**수락기준**:

- [ ] 재배포 시 이전 포트를 자동 제안한다
- [ ] 이전 배포의 환경변수를 기억하고 제안한다
- [ ] 같은 레포가 이미 clone 되어있으면 git pull만 수행한다
- [ ] 이전 빌드 실패 원인을 기억하고 대응 방안을 제안한다
- [ ] 제안은 에이전트 대화로 표시 (자동 적용은 포트만, 나머지는 확인 후)
- [ ] 테스트: 재배포 포트 유지, 환경변수 기억, 빌드 실패 히스토리 시나리오

### 11-4: Idle Scan (유휴 시 서버 점검)

**트리거**: 유저가 5분 이상 미입력 + TUI 열려있음 (MCP/Bot 채널은 제외)

유휴 상태에서 에이전트가 백그라운드로 서버를 스캔하고, 주목할 만한 것이 있으면 **한 번만** 채팅에 표시.

**점검 항목**:

| 항목             | 메시지 예시                                          |
| ---------------- | ---------------------------------------------------- |
| 미사용 컨테이너  | `💡 3개 컨테이너가 24시간+ 트래픽 없어. 정리 대상?`  |
| 미사용 이미지    | `💡 dangling 이미지 2.3GB. docker image prune 할까?` |
| 인증서 만료 임박 | `⚠️ frontend.example.com SSL 인증서 7일 후 만료.`    |
| 업데이트 가능    | `📋 ext-postgres 이미지에 새 버전(16.3)이 있어.`     |

**소음 방지**:

- **하루 1회**만 idle scan 수행 (같은 내용 반복 방지)
- 아무것도 발견 안 하면 **아무 말도 안 함**
- 유저가 "나중에"라고 하면 해당 항목 24시간 무시

**수락기준**:

- [ ] TUI에서 5분 미입력 시 백그라운드 서버 스캔을 실행한다
- [ ] 미사용 컨테이너 (24시간+ 비활성) 을 감지하고 정리를 제안한다
- [ ] dangling Docker 이미지를 감지하고 정리를 제안한다
- [ ] 하루 1회만 수행, 동일 내용 반복 방지
- [ ] MCP/Bot 채널에서는 idle scan을 수행하지 않는다
- [ ] 발견 사항이 없으면 아무 메시지도 표시하지 않는다
- [ ] 테스트: idle 감지, 미사용 컨테이너 발견, 반복 방지 시나리오

## 구현하지 않는 것

| 기능                                          | 왜 안 하는가                                    |
| --------------------------------------------- | ----------------------------------------------- |
| 자율 실행 (자동 정리, 자동 재시작)            | 인프라에서 자율 실행은 위험. DEC-001 원칙 적용. |
| 실시간 대시보드 이상 징후 표시                | TUI 복잡도 증가. 채팅 메시지로 충분.            |
| 학습 기반 예측 ("다음 주에 디스크 부족 예상") | 데이터 부족 + 복잡도. 추후 검토.                |
| 알림 규칙 커스터마이징 UI                     | 오버엔지니어링. 하드코딩 임계값으로 시작.       |

## 구현 순서 (의존성 기반)

```
Phase 1 (킬러): 11-1 Post-Deploy Insight
   ↓
Phase 2 (기반): 11-3 Smart Defaults
   ↓
Phase 3 (모니터링): 11-2 Anomaly Nudge
   ↓
Phase 4 (부가): 11-4 Idle Scan
```

**11-1이 먼저인 이유**: 가장 자연스러운 타이밍(배포 직후), 구현 난이도 낮음, 체감 효과 최고.
**11-3이 11-2보다 먼저인 이유**: Smart Defaults는 프롬프트 확장만으로 구현 가능. Anomaly는 새 모니터링 루프 필요.

## 공수 추정

| Phase          | 공수       | 사유                                                    |
| -------------- | ---------- | ------------------------------------------------------- |
| Phase 1 (11-1) | 1-2일      | deploy:success 이벤트 후크 + 인사이트 생성 + 채팅 주입  |
| Phase 2 (11-3) | 2일        | 배포 히스토리 조회 + 프롬프트 확장 + 스마트 기본값 로직 |
| Phase 3 (11-2) | 3-4일      | anomaly 감지 루프 + 소음 방지 + 묵음 처리               |
| Phase 4 (11-4) | 2일        | idle 감지 + 백그라운드 스캔 + 하루 1회 제한             |
| **총합**       | **8-10일** |                                                         |

## 우선순위 제안

현재 로드맵: `v0.0.9(✅)` → `v0.0.10(env)` → `v0.0.8(AI SDK)` → ...

**PM 의견**: v0.0.11을 v0.0.10보다 먼저 하는 것을 권장.

| 기준        | v0.0.10 (Env & Secrets)         | v0.0.11 (Agent Proactivity)  |
| ----------- | ------------------------------- | ---------------------------- |
| 유저 체감   | 중간 (이미 프로젝트별 env 있음) | **높음** ("이건 AI다" 순간)  |
| 제품 정체성 | 보조 기능                       | **핵심 차별화**              |
| 경쟁 대응   | Coolify도 env 관리 있음         | **아무도 안 하고 있음**      |
| 기술 리스크 | 낮음 (DB 스키마 + CRUD)         | 중간 (이벤트 훅 + 소음 방지) |
| 공수        | ~6일                            | ~8-10일                      |

→ **v0.0.11 (Phase 1: Post-Deploy Insight만이라도)을 먼저 하면, 도그푸딩에서 "AI 체감"을 검증할 수 있다.**
→ 최종 결정은 User에게.
