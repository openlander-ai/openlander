## 핵심 원칙

1. **기존 인프라를 절대 건드리지 않는다** — 감지와 관찰만. 명시적 동의 없이 설정 변경 없음.
2. **점진적 도입** — 관찰 → Import → 완전 관리 순서로 단계적 전환.
3. **공존 우선** — OpenLander가 기존 Traefik/프록시와 충돌 없이 공존.
4. **내 코드는 건드리지 않는다** — 로컬 개발 모드에서 의존성만 컨테이너화, 내 코드는 로컬 실행.

## Part 1: Docker 컨테이너 디스커버리 (v0.0.9)

### 1.1 배경

OpenLander는 현재 **자체 배포한 프로젝트만** 관리한다. 기존에 Docker로 직접 운영하던 컨테이너는:

- Status 패널에 보이지 않음
- 모니터링/로그/재배포 불가
- Traefik 라우팅과 충돌 가능

→ 기존 Docker 유저 입장에서 "이미 돌고 있는 것들은?" 이 첫 번째 질문이 된다.

타겟 유저:

- 개발서버에 Docker 컨테이너 10~20개 이미 운영 중
- docker-compose로 서비스 묶어서 관리하는 유저
- Traefik/Nginx 등 리버스 프록시를 이미 사용 중인 유저
- OpenLander를 "추가 도구"로 도입하려는 유저 (기존 인프라 교체가 아님)

### 1.2 자동 감지 (온보딩 + 시작 시)

OpenLander 최초 실행 시 `docker ps -a`로 기존 컨테이너를 스캔한다.

```
🔍 기존 Docker 환경 감지 중...

14개 컨테이너 발견:
  ● running (11)    ○ stopped (3)

  ● frontend         :3000   next.js       2d ago    128M
  ● backend          :8080   node          2d ago    256M
  ● postgres         :5432   postgres:15   5d ago    64M
  ● redis            :6379   redis:7       5d ago    32M
  ● nginx            :80     nginx:latest  5d ago    8M
  ● grafana          :3001   grafana       1w ago    96M
  ...
  ○ old-demo         —       node          3w ago    —
  ○ test-api         —       python        2w ago    —

OpenLander로 관리할까요?
  1. 전부 가져오기 (권장)
  2. 선택해서 가져오기
  3. 나중에 하기 — 새 배포만 관리
```

### 1.3 Import 프로세스

Import = DB에 프로젝트로 등록 + 메타데이터 수집. **컨테이너 자체는 건드리지 않는다.**

```
Import 시 수집하는 정보:
├─ 컨테이너 이름 → 프로젝트명
├─ 이미지 정보 (이름, 태그, sha256)
├─ 포트 매핑 (host:container)
├─ 환경변수 (docker inspect) → Project Variables에 등록 (Part 4 참조)
├─ 볼륨 마운트
├─ 네트워크 설정
├─ 리소스 사용량 (docker stats)
├─ Compose 관계 (com.docker.compose.project 라벨)
└─ 생성일, 상태, 재시작 횟수
```

**Import 후 가능해지는 것:**

| 기능             | Import 전 | Import 후          |
| ---------------- | --------- | ------------------ |
| Status 패널 표시 | ✗         | ✓                  |
| 리소스 모니터링  | ✗         | ✓                  |
| 로그 조회        | ✗         | ✓ (디버깅 모드)    |
| 중지/재시작      | ✗         | ✓                  |
| 재배포           | ✗         | △ (이미지 기반만)  |
| Git 연동 재배포  | ✗         | ✗ (수동 연결 필요) |

### 1.4 관찰 모드 (Import 없이)

Import를 하지 않아도, Status 패널에서 **전체 Docker 컨테이너를 볼 수 있는 관찰 모드**를 제공한다. Dashboard 3섹션 구조는 Part 5.1 참조.

### 1.5 Compose 그룹 인식

`com.docker.compose.project` 라벨로 Compose 그룹을 자동 인식한다.

```
▸ Discovered (외부 컨테이너)
  ▼ myapp-stack (compose, 4 services)
      ● frontend    :3000   128M
      ● backend     :8080   256M
      ● postgres    :5432   64M
      ● redis       :6379   32M
  ● grafana        :3001   96M
  ● nginx          :80     8M
  ...
```

Import 시 Compose 그룹은 하나의 프로젝트로 묶어서 등록한다 (기존 Compose 배포 기능과 동일한 parent-child 구조).

## Part 2: Traefik 공존 (v0.0.9)

### 2.1 문제

OpenLander는 기본적으로 Traefik을 자체 실행한다. 그런데 유저가 이미 Traefik을 쓰고 있으면:

- **포트 충돌** — 80, 443, 8080 이미 사용 중
- **이중 프록시** — 어느 Traefik이 요청을 받을지 모호
- **라벨 충돌** — Docker label 라우팅이 어느 인스턴스로 갈지 불확실

### 2.2 온보딩 감지

```
🔍 리버스 프록시 감지 중...

⚠ Traefik이 이미 실행 중입니다
  Container: traefik (running)
  Ports: 80, 443, 8080
  Version: v2.10.4
  Docker Provider: enabled

어떻게 할까요?
  1. 기존 Traefik 사용 (권장)
     → OpenLander가 Traefik을 띄우지 않고, 기존 Traefik에 라벨만 추가
  2. 별도 Traefik 실행
     → 다른 포트(10080/10443)로 OpenLander 전용 Traefik 실행
  3. 기존 Traefik 교체
     → OpenLander가 관리하는 Traefik으로 전환 (기존 설정 백업)
```

### 2.3 Traefik 모드

| 모드             | 설명                                     | 사용 시나리오                |
| ---------------- | ---------------------------------------- | ---------------------------- |
| `managed` (기본) | OpenLander가 Traefik을 띄우고 관리       | 새 환경, Traefik 없음        |
| `external`       | 기존 Traefik 사용, 라벨만 추가           | 이미 Traefik 운영 중         |
| `coexist`        | 별도 포트로 OpenLander 전용 Traefik 실행 | 기존 프록시 건드리기 싫을 때 |

**설정 저장:**

```json
{
  "traefik": {
    "mode": "external",
    "network": "traefik-net",
    "existingContainer": "traefik",
    "httpPort": 80,
    "httpsPort": 443
  }
}
```

### 2.4 `external` 모드 동작

기존 Traefik의 Docker provider가 활성화되어 있으면, 컨테이너에 Traefik 라벨만 추가하면 라우팅이 자동으로 잡힌다.

**OpenLander가 하는 것:**

1. 배포 시 컨테이너에 Traefik 라벨 추가 (기존과 동일)
2. 기존 Traefik의 Docker 네트워크에 컨테이너 연결
3. Traefik 컨테이너 자체는 띄우지 않음

**OpenLander가 하지 않는 것:**

- Traefik 설정 수정
- Traefik 재시작
- 기존 라우팅 규칙 변경

### 2.5 기타 리버스 프록시 감지

Traefik 외에 Nginx, Caddy, HAProxy도 감지한다.

```
감지 대상:
├─ traefik    → external 모드 지원 (라벨 기반)
├─ nginx      → coexist 모드 권장 (설정 파일 기반이라 자동 연동 어려움)
├─ caddy      → coexist 모드 권장
└─ haproxy    → coexist 모드 권장
```

Traefik만 `external` 모드를 완전 지원한다 (Docker label 기반이라 자동 연동 가능). 나머지는 `coexist` 모드로 별도 포트 운영을 권장한다.

## Part 3: Local Dev Mode (v0.0.10)

### 3.1 배경

개발자가 새 프로젝트에 투입되면 겪는 현실:

```
1. README 읽기 (있으면 다행)
2. docker-compose.yml 찾기 (없으면 직접 작성)
3. 환경변수 세팅 (.env 만들기)
4. docker compose up
5. 에러 → 버전 안 맞음 → 포트 충돌 → 30분~2시간 날림
6. 드디어 npm run dev
```

OpenLander Local Dev Mode는 이 과정을 채팅 한 줄로 줄인다.

### 3.2 핵심 개념

```
배포 모드:      git clone → build → run → expose (전체 서비스 컨테이너화)
로컬 개발 모드:  의존성만 컨테이너 → 내 코드는 로컬 실행
```

**내 코드는 건드리지 않는다.** 핫 리로드가 돼야 하니까 컨테이너에 넣지 않는다.
내 코드가 의존하는 인프라(DB, 캐시, 큐, 다른 서비스)만 OpenLander가 띄운다.

### 3.3 사용 시나리오

#### 시나리오 1: 의존성 인프라 즉석 실행

```
You: PostgreSQL 16이랑 Redis 띄워줘

✅ PostgreSQL 16 → localhost:5432
   user: postgres / pass: postgres / db: dev
✅ Redis 7 → localhost:6379

.env 생성할까요? (y/n)
> y

📄 .env 생성 완료:
  DATABASE_URL=postgres://postgres:postgres@localhost:5432/dev
  REDIS_URL=redis://localhost:6379
```

#### 시나리오 2: 프로젝트 README/compose 기반 자동 분석

```
You: 이 프로젝트 로컬에서 개발하려면 뭐 필요해?

🔍 프로젝트 분석 중...

  docker-compose.yml 발견:
    - PostgreSQL 16 (port 5432)
    - Redis 7 (port 6379)
    - Elasticsearch 8 (port 9200)

  package.json 분석:
    - Node.js 20+ 필요
    - npm run dev → Next.js dev server

의존성 인프라를 띄울까요? (y/n)
> y

✅ PostgreSQL 16 → localhost:5432
✅ Redis 7 → localhost:6379
✅ Elasticsearch 8 → localhost:9200

이제 npm run dev 하면 됩니다.
```

#### 시나리오 3: DB 초기 데이터 적용

```
You: DB 띄우고 schema.sql 적용해줘

✅ PostgreSQL 16 → localhost:5432
🔄 Applying schema.sql...
✅ 12 tables created

시드 데이터도 있네요 (seed.sql). 적용할까요? (y/n)
> y

✅ 245 rows inserted
```

#### 시나리오 4: 다른 팀 서비스 로컬 실행

```
You: 프론트 개발하려는데 백엔드 API가 필요해.
     github.com/team/backend-api 최신 버전으로 띄워줘.

🔄 Cloning team/backend-api...
🔄 Building...
✅ backend-api → localhost:8080

API_URL=http://localhost:8080 을 .env에 추가할까요? (y/n)
```

이 경우는 배포 모드와 동일한 파이프라인을 쓰되, Traefik 도메인 연결 없이 localhost 포트만 노출.

#### 시나리오 5: 로컬 프로젝트 빌드 → 외부 접속

git repo가 아닌 로컬 디렉토리를 빌드하여 외부에서 접속 가능하게 한다.
ngrok 대체. Cloudflare Tunnel이 이미 OpenLander에 있으므로 추가 설치 없음.

```
You: 현재 디렉토리 빌드해서 외부에서 접속 가능하게 해줘

🔍 /home/dongbin/my-project 분석 중...
🔄 Building...
🔄 Cloudflare Tunnel 연결 중...
✅ https://my-project-abc123.openlander.dev

이 URL로 외부에서 접속 가능합니다.
/stop 으로 종료.
```

기존 배포 파이프라인에서 입력 소스만 다르다:

```
git repo:   clone → build → run → expose
로컬 경로:  copy  → build → run → expose
```

clone 대신 로컬 디렉토리를 Docker 빌드 컨텍스트로 사용하는 것뿐. 나머지 동일.

사용 사례:

- 클라이언트에게 데모 보여주기
- Stripe/Slack webhook 테스트 (외부 URL 필요)
- 동료에게 로컬 작업물 공유

주의: Cloudflare Tunnel 설정이 필요하다. 온보딩에서 스킵했으면 `/tunnel`에서 설정.

### 3.4 배포 모드와의 차이

|          | 배포 모드            | 로컬 개발 모드         | 로컬 경로 배포               |
| -------- | -------------------- | ---------------------- | ---------------------------- |
| 입력     | git repo URL         | 채팅 (인프라명)        | 로컬 디렉토리 경로           |
| 대상     | 내 코드 전체         | 의존성 인프라만        | 내 코드 전체                 |
| 빌드     | 내 코드 빌드         | 공식 이미지 pull       | 내 코드 빌드                 |
| 네트워크 | Traefik → 도메인     | localhost 포트         | Cloudflare Tunnel → 외부 URL |
| 목적     | 팀에 서비스 제공     | 내 로컬 개발 환경 구성 | 데모/테스트/공유             |
| 속도     | 분 단위 (clone+빌드) | 초 단위 (이미지 pull)  | 분 단위 (빌드)               |

### 3.5 볼륨/데이터 영속성

```
기본 동작:
  - DB 데이터는 Docker named volume에 저장
  - /stop 해도 데이터 유지
  - 명시적으로 삭제해야 사라짐

채팅 UX:
  You: PostgreSQL 데이터 초기화해줘

  ⚠ dev_postgres_data 볼륨을 삭제합니다.
     모든 데이터가 사라집니다. 계속할까요? (y/n)
```

### 3.6 로컬 개발 모드 전용 기능

#### DB GUI 연결 정보

인프라 띄운 후 GUI 툴(DBeaver, pgAdmin 등) 연결 정보를 바로 보여준다:

```
✅ PostgreSQL 16 → localhost:5432

  연결 정보:
  Host:     localhost
  Port:     5432
  User:     postgres
  Password: postgres
  Database: dev

  연결 문자열:
  postgres://postgres:postgres@localhost:5432/dev
```

#### 헬스체크

인프라가 실제로 ready 상태인지 확인 후 완료 메시지 표시.

```
✅ PostgreSQL 16 → localhost:5432 (ready, accepting connections)
```

단순히 컨테이너 started가 아니라, 실제 연결 가능한 상태까지 확인.
PostgreSQL은 `pg_isready`, Redis는 `redis-cli ping`, Elasticsearch는 `/_cluster/health` 등.

## Part 4: 환경변수 관리 (v0.0.10)

### 4.1 배경

팀이 OpenLander를 쓰면 즉시 부딪히는 문제:

```
"이 프로젝트 배포하려면 OPENAI_API_KEY 어디서 가져와?"
"누가 DB 패스워드 바꿨어? 내 서비스 터졌는데"
"API key를 .env에 평문으로 넣으라고?"
```

Jenkins의 Credentials Store, GitHub Actions의 Secrets처럼
OpenLander도 환경변수/시크릿 중앙 관리가 필요하다.

### 4.2 환경변수 스코프

```
┌─────────────────────────────────────┐
│ Global Secrets                      │  ← 전체 프로젝트 공용
│   OPENAI_API_KEY=sk-...             │
│   DOCKER_REGISTRY_TOKEN=...         │
│                                     │
│ ┌─────────────────────────────────┐ │
│ │ Project: frontend               │ │  ← 프로젝트 전용
│ │   API_URL=https://api.mysite.com│ │
│ │   NODE_ENV=production           │ │
│ │                                 │ │
│ │ ┌───────────────────────────┐   │ │
│ │ │ User: dongbin             │   │ │  ← 개인 오버라이드
│ │ │   DEBUG=true              │   │ │
│ │ │   API_URL=http://localhost│   │ │
│ │ └───────────────────────────┘   │ │
│ └─────────────────────────────────┘ │
└─────────────────────────────────────┘
```

3단계 스코프. 좁은 스코프가 넓은 스코프를 오버라이드한다:

```
적용 우선순위: User > Project > Global
```

### 4.3 스코프 상세

#### Global Secrets (전체 공용)

모든 프로젝트에서 사용하는 시크릿.

```
예시:
  OPENAI_API_KEY       → 팀 공용 API 키
  ANTHROPIC_API_KEY    → 팀 공용 API 키
  DOCKER_REGISTRY      → 프라이빗 레지스트리 주소
  SENTRY_DSN           → 에러 트래킹
  SLACK_WEBHOOK_URL    → 알림
```

- 설정 권한: 관리자 (서버 소유자)
- 읽기: 모든 프로젝트 빌드/실행 시 자동 주입
- 채팅에서 값 표시 시 마스킹: `sk-...a3f2`

#### Project Variables (프로젝트 전용)

특정 프로젝트에만 필요한 변수.

```
예시:
  DATABASE_URL         → 이 프로젝트 전용 DB
  REDIS_URL            → 이 프로젝트 전용 캐시
  API_URL              → 연동 서비스 주소
  NODE_ENV             → production / development
  PORT                 → 서비스 포트
```

- 설정 권한: 해당 프로젝트 배포자
- 배포 시 자동 주입
- 프로젝트 간 격리 (frontend의 변수가 backend에 안 들어감)

#### User Overrides (개인 오버라이드)

개발자별 로컬 개발 시 사용하는 오버라이드.

```
예시:
  DEBUG=true                          → 디버그 모드
  API_URL=http://localhost:8080       → 로컬 API 연결
  LOG_LEVEL=verbose                   → 상세 로그
```

- 다른 사람에게 영향 없음
- 로컬 개발 모드에서 주로 사용
- 배포 모드에서는 적용되지 않음 (실수 방지)

### 4.4 Import된 프로젝트의 환경변수 매핑

> Part 1 디스커버리에서 Import한 프로젝트의 환경변수가 스코프 시스템에 어떻게 들어오는지 정의한다.

Import 시 `docker inspect`로 수집한 환경변수는 다음 규칙으로 분류:

```
Import 환경변수 자동 분류:
├─ Global Secrets에 동일 키가 이미 존재
│   → 스킵 (Global 값 우선, 유저에게 알림)
│   → "OPENAI_API_KEY는 Global에 이미 등록되어 있어 스킵합니다."
│
├─ 키 이름에 KEY, SECRET, TOKEN, PASSWORD 포함
│   → Project Variables (암호화 저장)
│   → "DB_PASSWORD를 frontend Project에 암호화 저장했습니다."
│
└─ 나머지
    → Project Variables (평문 저장)
    → "NODE_ENV=production을 frontend Project에 저장했습니다."
```

**채팅 UX:**

```
You: myapp-stack Import 해줘

🔄 Import 중...
✅ 4개 서비스 등록 완료

📋 환경변수 처리:
   Global에서 가져옴:  OPENAI_API_KEY (이미 등록됨)
   Project에 저장:     DATABASE_URL 🔒, REDIS_URL, NODE_ENV, PORT
   확인 필요:          CUSTOM_SECRET (값이 비어있음)

CUSTOM_SECRET 값을 입력해주세요:
> ...
```

### 4.5 저장

```
~/.openlander/
├── secrets.enc          ← Global Secrets (암호화)
├── projects/
│   ├── frontend.env     ← Project Variables
│   └── backend.env
└── users/
    ├── dongbin.env      ← User Overrides
    └── jihye.env
```

#### 암호화

- Global Secrets는 반드시 암호화 저장 (평문 저장 금지)
- 암호화 키: 온보딩 시 자동 생성, `~/.openlander/master.key`에 저장
- Project Variables: 민감한 값은 암호화, 일반 값은 평문
- User Overrides: 평문 (개인 개발용이라 민감도 낮음)

## Part 5: 통합 UI/UX

> 기존 두 문서에서 각각 정의했던 Dashboard, 포트 관리, 온보딩, 슬래시 명령을 통합 정리한다.

### 5.1 Dashboard 3섹션 구조

OpenLander가 관리하는 컨테이너는 3가지 출처가 있다. Status 패널에서 이를 구분 표시:

```
▸ Projects (배포)                          ← OpenLander가 배포한 프로젝트
  ● frontend  :3000  128M
    app.mysite.com
  ● api-server :8080 256M
    api.mysite.com

▸ Discovered (외부 컨테이너)               ← 감지/Import된 외부 컨테이너 (v0.0.9)
  ● nginx      :80    8M       imported
  ● grafana    :3001  96M      imported
  ○ old-demo   —      —        관찰만
  ...
  Import로 관리 전환 가능

▸ Infra (로컬 개발)                        ← 로컬 개발용 인프라 (v0.0.10)
  ● postgres   :5432  128M    vol: 240MB
  ● redis      :6379  32M
  ● elastic    :9200  512M    vol: 1.2GB
```

**섹션 표시 규칙:**

| 섹션       | 표시 조건                       | 소스             |
| ---------- | ------------------------------- | ---------------- |
| Projects   | 항상 표시 (0개여도)             | OpenLander 배포  |
| Discovered | 외부 컨테이너가 감지되었을 때만 | `docker ps` 스캔 |
| Infra      | 로컬 인프라가 실행 중일 때만    | 로컬 개발 모드   |

**Discovered 섹션 내 상태 구분:**

- `imported` — DB에 등록됨. 모니터링/로그/중지/재시작 가능.
- `관찰만` — 감지만 됨. Status 표시만.

Infra 섹션은 볼륨 사이즈 표시 (DB는 데이터가 쌓이므로 디스크 관리 필요).

### 5.2 포트 관리 (공유 유틸리티)

포트 충돌 관리가 두 가지 맥락에서 필요하다. **동일한 포트 스캔 유틸리티**를 공유한다.

#### 5.2.1 기존 컨테이너 포트 충돌 감지 (v0.0.9)

온보딩/시작 시 현재 사용 중인 포트를 스캔하여 OpenLander 기본 포트와 충돌을 감지:

```typescript
interface PortScan {
  inUse: number[]; // 현재 사용 중인 포트
  conflicts: number[]; // OpenLander 기본 포트(80, 443, 8080)와 충돌
}
```

#### 5.2.2 멀티유저 포트 자동 분리 (v0.0.10)

같은 서버에서 여러 개발자가 로컬 인프라를 띄우면 포트가 충돌한다:

```
dongbin:  postgres → :5432
jihye:    postgres → :5433 (5432 충돌 → 자동 할당)
```

유저별로 포트 대역을 자동 할당하고, 생성되는 .env에 실제 할당된 포트 반영.

#### 5.2.3 공유 모듈

```
src/docker/port-scanner.ts  ← 공유 유틸리티
├─ scanUsedPorts()          → 현재 사용 중인 포트 목록
├─ findAvailablePort(base)  → base 포트부터 빈 포트 탐색
├─ checkConflicts(ports[])  → OpenLander 기본 포트와 충돌 확인
└─ allocateUserPort(user, service)  → 유저별 포트 할당
```

v0.0.9(기존 컨테이너 감지)와 v0.0.10(멀티유저 포트 분리) 모두 이 모듈을 사용한다.

### 5.3 온보딩 플로우 (통합)

```
1. Docker 설치 확인
2. 기존 환경 스캔                    ← v0.0.9
   ├─ 기존 Docker 컨테이너 감지 → Import 제안
   ├─ 리버스 프록시 감지 → Traefik 모드 설정
   └─ 포트 사용 현황 스캔 → 충돌 방지
3. LLM API 키 설정
4. Git 연결 (선택)                   ← /git 참조 (5.4절)
5. Cloudflare Tunnel 설정 (선택)     ← /tunnel 참조
6. 완료
```

**환경 스캔 상세 (EnvironmentScan):**

```typescript
interface EnvironmentScan {
  containers: {
    total: number;
    running: number;
    stopped: number;
    items: ContainerInfo[];
    composeGroups: ComposeGroup[];
  };
  proxy: {
    type: 'traefik' | 'nginx' | 'caddy' | 'haproxy' | 'none';
    container?: string;
    ports: number[];
    version?: string;
    traefikDockerProvider?: boolean;
  };
  ports: {
    inUse: number[];

```

### 5.5 상태바

```
모니터링: │ 3 projects + 11 containers + 3 infra │ CPU 12% MEM 4.2G │ Tab:패널 ?:도움말
```

- `3 projects` = OpenLander 배포 프로젝트
- `11 containers` = 감지/Import된 외부 컨테이너 (0이면 생략)
- `3 infra` = 로컬 개발 인프라 (0이면 생략)

### 5.6 "기존 거 망가뜨리면 어쩌지?" 불안감 해소

1. **Import 시 명확한 안내**: "컨테이너를 건드리지 않습니다. DB에 등록만 합니다."
2. **Undo 지원**: Import 취소 = DB에서 삭제. 컨테이너는 그대로.
3. **관찰 모드 먼저**: Import 안 해도 볼 수 있음 → 신뢰 구축 후 Import.
4. **Traefik external 모드**: "기존 설정 안 건드립니다" 명시.
