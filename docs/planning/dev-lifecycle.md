# OpenLander — 개발 라이프사이클

> **목적**: 기능 기획부터 릴리즈까지의 전체 흐름 정의.
> 모든 역할(User, PM, Tech Lead)이 이 문서를 공유 참조점으로 사용한다.

---

## 역할 정의

| 역할             | 스킬            | 누가                 | 핵심 책임                                     |
| ---------------- | --------------- | -------------------- | --------------------------------------------- |
| **User**         | —               | 사람 (프로젝트 오너) | 아이디어, 방향 결정, 도그푸딩, 최종 승인      |
| **PM**           | `project-owner` | AI 에이전트          | 스펙 문서화, 테스트 계획, 버그 트리아지, 검수 |
| **Tech Lead**    | `tech-lead`     | AI 에이전트          | 스펙 리뷰, 태스크 분해, 구현/위임, Phase 검증 |
| **Quality Gate** | `quality-gate`  | 스킬 (자동)          | build/test/lint 통과 확인                     |

---

## 전체 플로우

```
[1] User: 아이디어/방향 제시
     │
[2] PM: 스펙 문서화 + 테스트 계획 초안
     │
[3] PM → Tech Lead: "검토해봐"
     │
[3.5] Tech Lead: 실현가능성 검토 + 피드백
     │   "공수 2배", "기준 모호", "엣지케이스 추가 필요"
     │
[4] PM: 스펙/테스트 보완 → 개발 확정 지시
     │
[5] Tech Lead: 태스크 분해 + 구현
     │
[6] Quality Gate: Phase별 자동 검증
     │
[6.5] Tech Lead → PM: 테스트 계획 보완 제안
     │   "구현 중 발견한 엣지케이스, 테스트에 추가 권장"
     │
[7] PM: 테스트 계획 확정 → User에게 전달
     │
[8] User: 도그푸딩 (1주)  ←──────┐
     │                            │
[9] PM: 버그 정리 + 수정 지시     │ 루프
     │                            │
[10] Tech Lead: 버그 수정 ────────┘
     │   (User가 "OK" 할 때까지)
     │
[11] PM: 최종 검수 → 버전 완료 선언
```

---

## 단계별 상세

### [1] User: 아이디어/방향 제시

**입력**: 구두, 채팅, 또는 간단한 메모
**출력**: PM이 해석할 수 있는 방향성

예시:

- "서버 상태를 에이전트가 알아야 해"
- "환경변수 암호화 필요"
- "배포 전에 충돌 검사하는 기능"

User는 구체적인 구현 방법을 정의할 필요 없다. "뭘 원하는지"만 명확하면 PM이 정리한다.

---

### [2] PM: 스펙 문서화 + 테스트 계획 초안

**입력**: User의 아이디어
**출력**:

- 스펙 문서 (`docs/planning/v0.0.X/*.md`)
- 테스트 계획 초안 (스펙 문서 내 또는 별도)
- version-map.md 갱신

**PM이 하는 것**:

1. User의 아이디어를 구조화된 스펙으로 변환
2. 수락기준 정의 (검증 가능한 형태)
3. 테스트 시나리오 초안 작성 (User가 도그푸딩 시 따를 체크리스트)
4. 기존 결정(decision-log.md)과 충돌 확인
5. 로드맵 반영

**테스트 계획 초안 형식**:

```markdown
## 수동 테스트 시나리오 (User 도그푸딩용)

### 시나리오 1: [시나리오명]

**사전 조건**: [서버에 외부 컨테이너 3개 이상 실행 중]
**절차**:

1. OpenLander 시작
2. Dashboard의 Server 섹션 확인
3. 외부 컨테이너 목록이 정확한지 검증

**기대 결과**: [모든 외부 컨테이너가 표시됨]
**확인 방법**: [docker ps 결과와 대조]
```

---

### [3] PM → Tech Lead: "검토해봐"

**입력**: 완성된 스펙 문서
**출력**: Tech Lead 리뷰 요청

PM이 Tech Lead에게 전달할 것:

- 스펙 문서 경로
- "이 스펙의 실현 가능성, 공수, 모호한 부분을 리뷰하고 피드백해줘"
- 구현 순서 제안 (Phase 순서)

---

### [3.5] Tech Lead: 실현가능성 검토 + 피드백

**입력**: 스펙 문서
**출력**: 리뷰 피드백

Tech Lead가 확인하는 것:

1. **실현 가능성** — 기술적으로 가능한가? 외부 의존성은?
2. **공수 추정** — Phase별 예상 소요 시간
3. **모호한 수락기준** — "적절히" 같은 표현 지적
4. **누락된 엣지케이스** — 스펙이 커버하지 않는 상황
5. **기존 코드 영향** — 수정 범위, 하위 호환 위험

**피드백 형식**:

```markdown
## Tech Lead 스펙 리뷰

### 공수 추정

- Phase 1: 3일 (예상대로)
- Phase 2: 5일 (스펙보다 1.5배 — OS 포트 스캔 플랫폼별 분기 때문)

### 모호한 부분

- 9-2: "OS 레벨 포트 스캔" — sudo 없이 ss -tln으로 충분한지, 아니면 프로세스 이름까지 필요한지
- 9-7: "리소스 부족" 임계값 미정의 (디스크 몇 GB 이하? 메모리 몇 %?)

### 누락된 엣지케이스

- Docker daemon이 중지된 상태에서 스캔 시도하면?
- 컨테이너가 100개 이상이면 성능 이슈?

### 위험

- port.ts의 findAvailablePort() 수정 없이 scanUsedPorts()만 추가하면,
  기존 배포 플로우에서 새 함수를 안 쓸 수 있음. 호출 지점 수정 범위 명확히.
```

---

### [4] PM: 스펙/테스트 보완 → 개발 확정 지시

**입력**: Tech Lead 피드백
**출력**:

- 보완된 스펙 문서 (모호한 부분 해소, 엣지케이스 추가)
- 보완된 테스트 계획
- 개발 확정 지시 ("Go")

PM이 하는 것:

1. Tech Lead 피드백을 스펙에 반영
2. 모호한 수락기준 구체화
3. 공수 추정에 따라 Phase 조정 (필요 시)
4. User에게 스코프 변경이 있으면 확인
5. "Go" 지시

---

### [5] Tech Lead: 태스크 분해 + 구현

**입력**: 확정된 스펙 + 개발 지시
**출력**: 코드, 단위 테스트

상세 → `tech-lead` 스킬의 워크플로우 참조.

---

### [6] Quality Gate: Phase별 자동 검증

**입력**: 구현된 코드
**출력**: 검증 결과 (pass/fail)

```
□ bun run build: exit code 0
□ bun test: 0 failures
□ lsp_diagnostics: 변경 파일 에러 0
□ 수락기준 1:1 대조
```

---

### [6.5] Tech Lead → PM: 테스트 계획 보완 제안

**입력**: 구현 과정에서 발견한 엣지케이스
**출력**: 테스트 시나리오 추가 제안

예시:

```
"구현 중 발견: 외부 컨테이너가 'restarting' 상태일 때 포트가 일시적으로 비어 보임.
 테스트 계획에 'restarting 컨테이너가 있는 상태에서 배포' 시나리오 추가 권장."
```

---

### [7] PM: 테스트 계획 확정 → User에게 전달

**입력**: 초안 테스트 계획 + Tech Lead 보완
**출력**: User가 따를 최종 테스트 체크리스트

형식:

```markdown
## v0.0.9 도그푸딩 체크리스트

### 환경 준비

- [ ] 서버에 OpenLander 외 컨테이너 최소 3개 실행
- [ ] 포트 80 사용하는 서비스 1개 이상

### 테스트 항목

- [ ] 시나리오 1: Dashboard Server 섹션에 외부 컨테이너 표시되는지
- [ ] 시나리오 2: 이미 사용 중인 포트로 배포 시 preflight 차단되는지
- [ ] 시나리오 3: MCP로 list_all_containers 호출 시 전체 반환되는지
- [ ] 시나리오 4: ...

### 버그 발견 시

채팅으로 보고. PM이 bugs.md + GitHub Issue 정리.
```

---

### [8-10] 도그푸딩 루프

```
User: "이거 안 돼" / "여기 이상해" / "이건 좋은데 저건 불편"
  ↓
PM: bugs.md에 BUG-NNN 추가 + GitHub Issue 생성
    심각도 분류 (blocking / major / minor)
    Tech Lead에게 수정 지시
  ↓
Tech Lead: 버그 수정 + Quality Gate 통과
  ↓
PM: bugs.md 업데이트 (활성 → 해결)
    User에게 "수정됨, 재테스트 부탁"
  ↓
User: 재테스트 → OK 또는 추가 버그
  ↓
(OK 될 때까지 반복)
```

**루프 종료 조건**:

- blocking 버그 0개
- major 버그 0개
- minor 버그는 User 판단 ("이건 다음 버전에 해도 돼")
- User가 "OK" 선언

---

### [11] PM: 최종 검수 → 버전 완료 선언

PM이 하는 것:

1. 모든 수락기준 최종 대조
2. version-map.md 상태 업데이트 (📋 → ✅)
3. bugs.md 정리 (미해결 → 다음 버전 이관)
4. CHANGELOG 갱신
5. README 로드맵 업데이트
6. User에게 "v0.0.9 완료" 보고

## 문서 간 관계

```
이 문서 (dev-lifecycle.md)
  ↓ 참조
┌─────────────────────────────────┐
│ project-owner SKILL.md          │  ← [2][3][4][7][9][11] 수행 방법
│ tech-lead SKILL.md              │  ← [3.5][5][6.5][10] 수행 방법
│ quality-gate SKILL.md           │  ← [6] 수행 방법
│ version-map.md                  │  ← 상태 추적
│ bugs.md                         │  ← 버그 추적
│ v0.0.X-*.md                     │  ← 스펙 문서
└─────────────────────────────────┘
```
