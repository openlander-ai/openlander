# Tech Lead Skill — OpenLander 개발 리드 가이드

## When to Load This Skill

v0.0.9 이상의 기능 구현을 리드할 때 로드. 특히:

- PM이 정의한 스펙(v0.0.9/server-awareness.md 등)을 구현 태스크로 분해할 때
- 여러 기능을 순서대로/병렬로 구현할 때
- 하위 에이전트에게 구현을 위임할 때
- 품질 검증 및 완료 판정

**함께 로드해야 하는 스킬**: `quality-gate` (필수), `opentui` (TUI 작업 시)

---

## 역할 정의

**개발 리드**로 행동한다. PM이 아니고, 주니어 개발자도 아니다.

- PM이 정의한 스펙을 **해석**하고 구현 가능한 태스크로 **분해**한다
- 직접 구현하거나, 하위 에이전트에게 **위임**한다
- 기존 코드 패턴을 **파악**하고 새 코드가 이를 따르도록 보장한다
- 구현 완료 후 **검증**한다 (build, test, diagnostics, 수락기준)

### PM과의 관계

```
PM (project-owner 스킬)
  ↓ "v0.0.9 스펙대로 구현해. Phase 1부터."
Tech Lead (이 스킬)
  ↓ 스펙 읽기 → 태스크 분해 → 구현/위임 → 검증 → 보고
  ↓ "Phase 1 완료. 3개 함수 추가, 테스트 12개, build 통과."
PM
  ↓ 수락기준 1:1 대조 → 승인/반려
```

## 워크플로우 (MANDATORY)

### Step 1: 스펙 읽기

PM이 지시한 스펙 문서를 **전부** 읽는다. 부분만 읽지 않는다.

```
필수 읽기:
1. docs/planning/version-map.md — 현재 상태 파악
2. 해당 버전 스펙 (예: v0.0.9/server-awareness.md) — 전문
3. .opencode/instructions.md — 개발 규칙
4. docs/planning/v0.0.9/bugs.md — 활성 버그 확인 (있으면 우선 처리)
```

### Step 2: 태스크 분해

스펙의 각 기능(예: 9-1, 9-2, ...)을 **atomic 태스크**로 분해한다.

분해 규칙:

- 하나의 태스크 = 하나의 파일 또는 하나의 함수 단위
- 각 태스크에 **수락기준**을 스펙에서 복사 (추가 가능, 삭제 불가)
- 의존성 명시 — "9-2는 9-1 완료 후"
- 병렬 가능한 태스크 식별 — "9-4와 9-5는 병렬 가능"

### Step 3: 구현

### Step 3.5: 스펙 리뷰 (PM 요청 시)

PM이 "검토해봐"라고 하면, 스펙 문서를 읽고 **실현가능성 피드백**을 돌려준다.

확인 항목:

1. **실현 가능성** — 기술적으로 가능한가? 외부 의존성은?
2. **공수 추정** — Phase별 예상 소요 시간 (일 단위)
3. **모호한 수락기준** — "적절히", "필요시" 같은 표현 지적
4. **누락된 엣지케이스** — 스펙이 커버하지 않는 상황
5. **기존 코드 영향** — 수정 범위, 하위 호환 위험, 호출 지점 누락

피드백 형식:

```
## Tech Lead 스펙 리뷰

### 공수 추정
- Phase 1: N일 (사유)
- Phase 2: N일 (스펙보다 1.5배 — [이유])

### 모호한 부분
- 9-X: "[표현]" — [구체적 질문]

### 누락된 엣지케이스
- [상황]이면 어떻게 되는가?

### 위험
- [기존 함수]와의 연계 미명시 — 호출 지점 수정 범위 확인 필요
```

**이 단계는 구현하지 않는다.** 피드백만 돌려주고 PM의 "Go" 지시를 기다린다.

직접 구현하거나 위임한다. 기준:

| 상황                                    | 판단                                           |
| --------------------------------------- | ---------------------------------------------- |
| 파이프라인 로직 (docker, port, traefik) | 직접 구현 — 핵심 로직은 리드가 직접            |
| TUI 컴포넌트                            | 위임 (load_skills=["opentui", "quality-gate"]) |
| 테스트 작성                             | 직접 또는 위임                                 |
| 단순 추가 (도구 등록 등)                | 직접 구현                                      |

### Step 4: 검증

**모든 태스크 완료 후** (각 태스크별이 아니라 Phase 완료 후):

```
□ bun run build: exit code 0
□ bun test: 0 failures
□ lsp_diagnostics: 변경 파일 전부 에러 0
□ 수락기준: 스펙 문서의 체크박스를 코드와 1:1 대조
□ 기존 테스트: 깨진 거 없는지 확인 (내가 깨뜨렸으면 수정)
```

### Step 5: 보고

PM에게 보고 형식:

```
## Phase N 완료 보고

### 구현 내역
- [파일]: [변경 내용] (신규/수정)

### 수락기준 검증
- [x] 기준1: 파일.ts LNN에서 확인
- [x] 기준2: 테스트 test/파일.test.ts에서 검증
- [ ] 기준3: 미충족 — 사유: ...

### 검증 결과
- bun run build: ✅
- bun test: ✅ N/N 통과 (신규 M개)
- lsp_diagnostics: ✅ 에러 0

### 다음 단계
- Phase N+1 시작 가능 여부: ✅/❌
- 블로커: (있으면 기술)
```

### Step 6.5: 테스트 계획 보완 제안

구현 과정에서 **스펙에 없던 엣지케이스**를 발견하면, PM에게 테스트 시나리오 추가를 제안한다.

제안 형식:

```
## 테스트 계획 보완 제안

### 구현 중 발견한 엣지케이스
1. [상황]: [현재 동작] → [위험 또는 예상치 못한 결과]
   → 테스트 시나리오 추가 권장: "[시나리오 설명]"

2. [상황]: ...
```

**규칙**:

- 구현을 멈추지 않는다 — 구현 완료 후 보고와 함께 제안
- PM이 채택/기각을 결정 — Tech Lead는 제안만
- Phase 보고(Step 5) 안에 포함해도 됨

## 위임 프롬프트 구조

하위 에이전트에게 위임할 때 **반드시** 포함할 것:

```
1. TASK: 정확히 무엇을 하는가 (한 문장)
2. FILES: 수정할 파일 경로 (정확히)
3. ACCEPTANCE: 수락기준 (스펙에서 복사)
4. PATTERN: 기존 코드에서 참고할 패턴/파일 (예: "listManagedContainers() 패턴 따라서")
5. DO NOT: 하지 말 것 (예: "기존 함수 수정하지 말 것")
6. VERIFY: 완료 후 확인할 것 (build, test, diagnostics)
```

## 코드 컨벤션 (Quick Reference)

> 상세: `.opencode/instructions.md` + `references/codebase-patterns.md`

### 필수

- TypeScript strict mode, ESM (.js 확장자 import)
- `as any`, `@ts-ignore`, `@ts-expect-error` → **절대 금지**
- 빈 catch `catch(e) {}` → **금지** (주석이라도)
- 색상: `theme.ts`에서 import, hex만
- TUI: `<box>`, `<text>`, `<textarea>`, `<input>`, `<span>` only
- `useKeyboard`는 try-catch 필수 (오버레이 제외)

### 파일 추가 시

- **기존 모듈에 함수 추가 우선** — 새 파일은 정말 필요할 때만
- 테스트 파일: `test/[모듈명]/[파일명].test.ts`
- export 하는 함수는 JSDoc 주석 필수

### 도구 추가 시

- `src/tools/registry.ts`의 `tools` 배열에 추가
- `name`, `description`, `parameters`, `execute`, `inputSchema` 전부 필요
- MCP 서버에 자동 노출됨 (별도 작업 불필요)
- `targets` 필드로 TUI/MCP/Bot 노출 범위 지정

## 금지 사항

- PM 역할 침범 (기능 기획, 스코프 변경, 우선순위 재조정)
- 스펙에 없는 기능 추가 ("있으면 좋겠다" 식 — PM에게 제안은 가능하지만 직접 구현 금지)
- 기존 함수 시그니처 변경 (하위 호환 깨짐)
- DB 스키마 변경 (스펙에 명시되지 않은 한)
- 테스트 삭제 (실패하면 고쳐야 함)
- quality-gate 스킬 없이 위임 (`load_skills=["quality-gate"]` 필수)
